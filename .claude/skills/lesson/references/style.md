# 读感

目标是读起来像 academy.claude.com 的课文：几分钟读完，每一段都不费劲，读到哪里都不用停下来查别处。Academy 各门课的讲法、版面各不相同（见 [讲法目录](skeletons.md)），但读感是同一种，由下面几件事构成。数字来自 59 篇 Academy 课文的实测（MCP 两门课、《使用 Claude API 构建》工具与智能体两章、Claude Code 101 与子代理 / 技能课、AI 能力与局限），`scripts/lesson_lint.py` 按同一组数字检查。

## 一课一个概念

每课只讲一个概念，正文（不算代码和组件）多在 600–1100 字。写不下时说明这一课装了两个概念，拆成两课，或者把细节挪进演练页；不要靠压缩句子塞下。

决定什么进正文，只问一个问题：**读者要懂这个概念，非知道不可吗？** 字段名、参数上限、函数之间怎么调用，这些是实现，放进演练；实现之外的边角，删掉，或收进“阅读更多”。

## 段落和句子

- **一段一个意思。** 两三句，平均 40–70 字，最长不过 120 字。
- **句子短，主语完整。** 一个句子交代一件事，少用分号把几件事串在一起。
- **导语短。** H1 下面一段两三句（至多三个短段），然后直接进第一个二级标题。照 Academy 的技能课、AI 能力课，也可以在导语后放一张“学完后，您将能够”清单卡（三四条），一门课里要么每课都有、要么都没有。

## 只讲它怎么工作

正文用讲课的口吻，直接陈述机制：“执行器先检查这个工具是否开启”。用“您”称呼读者，“我们”用得少。

- **具名场景一个就够。** 从读者的世界里取一个具体场景，名字和数字取自代码：顾客的一句话、一件商品。整课都用它；正文不写商品 ID 这类标识，留给演练页。图和消息流里引用真实结果的原话时，ID 照原样保留。
- **代码名少而准。** 正文里只留读者在演练里会再见到的一两个名字（比如工具名），第一次出现时并列中文叫法（“来源门控（`provenance`）”），之后全课只用一个叫法。代码实操课例外，代码本身就是主角。
- **数字只留本身就是重点的。** 比如“每轮请求的工具定义逐字节相同”里的“逐字节”；字符上限、行数这类细节不进正文。
- **核对是写之前的事。** 每句话都要对得上代码，但正文直接说结论，不交代出处：注释和测试里写了什么、规则编号、指南原话，都不进正文。
- **比喻至多一个。** 用“更接近 A 而不是 B”的句式轻轻带过。

## 承接与收尾

- **开头至多半句承接**：“编写完工具函数后，下一步是……”，只说内容。
- **中段只讲这一课**：要用到前面的知识时，用“请记住，……”把那句话直接说出来，读者不必翻回去。
- **收尾按课型选**（见 [讲法目录](skeletons.md) 的“收尾”）：“何时使用 X + 一句本质”、“回顾”、“接下来”、关键要点、自测清单或一句格言。提到下一课只在收尾这一节，一次。

## 小标题

小标题让读者随时知道自己在哪：用概念名加角度，同一个概念名在各个小标题里重复出现，目录读起来就是这一课的提纲。

```text
Sampling 解决的问题 → Sampling 的工作原理 → Sampling 的优势 → 实现方式 → 何时使用 Sampling
Claude Code 与 Claude 有何不同 → 智能体循环 → 上下文 → 工具 → 权限 → 回顾
```

## 图文节奏

- **讲问题和机制时，每一两段一张图或一个让读者动手的组件。** 一课 1–4 张图；优势、何时使用这类收尾小节不配图。
- **先一句冒号引导，再图，图后一两句解释。** 对照两个选项时，每张图后跟一段“**选项 1：** ……”。
- **对照、清单写成粗体标签列表**（“**降低服务器复杂性：** 服务器不需要直接集成语言模型”）或成对小节；Academy 课文里没有表格。
- **提示块一课至多一两个**，只用 Academy 用过的两种：一节末尾的 `:::tip[小提示]`，收尾的 `:::important[关键要点]`。

## 改写前后

**导语和问题。** 改写前，导语三段，交代了上一课、参考实现和本课目标，第一个小标题下又先解释原型店铺：

> 一个 Agent 工具由两半组成：模型读到的**定义**，和执行器运行的**代码**。定义告诉模型能做什么、参数怎么填；代码把这次调用交给商店已有的系统。两半之间的那条线就是工具边界：线的一侧是模型的判断，另一侧是系统的逻辑。
>
> 在《循环与第一个工具》里，我们用一个 Python 函数在六条示例商品里做关键词匹配……默认配置下它有 21 个工具……
>
> 读完这一节，您将能够说出……

改写后（用户确认的读感）：

> 工具把商店已有的系统接给模型。模型只决定搜什么，检索、排序和校验都留在系统一侧。这条分工线就是工具边界。
>
> ## 工具边界解决的问题
>
> 假设顾客问：“有没有 200 美元以内的双人帐篷？”Agent 得先找出帐篷，再去掉超预算的。您有两个选择：
>
> （图：整个商品目录摊在模型面前）
>
> **选项 1：** 把整个目录放进上下文，让模型自己筛。几件商品时可行，但真实商店的目录放不进上下文，模型也看不到商店的排序信号。
>
> （图：模型发出一次搜索，商店返回结果）
>
> **选项 2：** 给模型一个搜索工具。模型只决定搜什么，找商品、排顺序交给商店自己的搜索系统。

**表格改成标签列表。** 改写前是一张五行的表，每行一句模型收到的原话。改写后只说每种失败该怎么办，原话留给演练：

> - **参数不合要求：** 告诉模型哪个字段错了，改了再调。
> - **商品买不了：** 请模型告诉顾客，推荐有货的替代品，等顾客自己选。
> - **本店不提供：** 请模型直接告诉顾客。
> - **工具出故障：** 请模型用手上已有的信息继续。

**演练一步。** 改写前两段约 200 字，提到七个代码名。改写后：

> **整理参数**
> 执行器先整理参数：关键词过长会被截断，筛选条件不合规就把出错的字段退回给模型。整理好的参数交给后端，执行器自己不做检索。
