# 讲稿转笔记

## 输入

用户通常这样调用，各项顺序随意，缺的就按下面的默认值处理：

```text
/note python/CPython
标题：CPython
位置：docs/python/        （可写子分组，如 python/装饰器）
文稿：
……讲稿全文……
代码：
……一段或多段代码，可带文件名或说明……
```

- **位置**：`$ARGUMENTS` 里最后一个斜杠前面的部分，或“位置：”一行，不带 `docs/`，对应 `docs/<位置>/`。
- **标题**：斜杠后面的部分，或“标题：”一行，用作 H1。文件名默认取标题：英文标题转成小写（如 `cpython.md`），中文标题去掉空格（如 `多线程.md`，“自建住宅 IP 节点”→ `自建住宅IP节点.md`）。和已有文件重名时先问用户。
- **文稿**：最长的那段口语文本。
- **代码**：用户贴出的代码块，或标着“代码 / 代码片段”的部分。没有代码就是纯科普，不加代码块；YouTube 讲稿里讲者让读者输入的命令另取，见 references/youtube.md。
- 位置和标题都推断不出来时，停下来问用户。除了下文写明要先问的几处（文件重名、旧版本 Python 的行为、找不到视频 ID），其余都不问，直接开始写。

原则：**正文是用户的内容，只做最小替换**；可以加的是小标题、链接、代码块这类结构性内容，而且每一处都要在最后逐条告诉用户。

为什么这么严：讲稿是用户本人的讲解，口语感就是用户本人的风格。之前润色成书面语、删掉“多余”的句子、加导语和提示块，都被用户要求撤回。只要拿不准一处改动算不算“最小”，就不改，并在报告里提出来。

## 步骤

1. **同步并读周边。** `git pull --ff-only`；列出目标目录，读两三篇同目录的笔记，看清写法（标题、代码块 `title=` / `showLineNumbers=`、`<Term>`、链接习惯）。
   - 目录下没有 frontmatter 就不加，但开头放了简介块的笔记一定要写 `description`：不写的话，Docusaurus 会拿简介的第一行（“◉ RackNerd低价VPS：”）当分类页卡片和搜索结果的摘要。
   - 要 `import` 的组件（`<CardGrid>`、`<CodeWalkthrough>`）才存成 `.mdx`；`ReadMore`、`Term` 这类全局注册的组件，`.md` 里就能用。
   - 放进子分组时，参照已有的 `_category_.json`。同目录笔记写了 `sidebar_position` 时，新笔记要插在两篇之间就用小数（如 `2.5`），不用改别的文件。
   - 讲稿来自 YouTube 频道视频时，先读 [references/youtube.md](references/youtube.md)：频道话术、命令、用字幕核对识别错误都只写在那里，后面每一步都和它一起用。
   - 完成标准：列出讲稿里提到的、站内已有笔记的话题（“之前我们讲过……”“这个以后专门讲”），以及每个话题对应的文件；YouTube 讲稿还要拿到视频 ID。

2. **转写正文。** 逐段照抄讲稿，只做以下改动：
   - 涉及视频的说法改成文章：“这期视频”→“这篇文章”，“之前几期”→“之前几篇”，“视频里听到”→“文章里看到”，“技术视频”→“技术文章”。讲稿提到同频道的另一期视频时，按 references/youtube.md 的“引用其他几期”处理，不要一律改成“文章”。
   - 按语境修语音识别错误：同音字、断句、英文术语拼写（如 “GIL 呢，或者 GIL 以后” → “GIL 呢，我们以后”）。
     只修“听错了”的地方，不修“说得不严谨”的地方：讲者自己的用词（比如把 Implementation 说成单数、说法不够精确）算讲稿内容，不改，有疑问写进报告。
   - 结尾如果是“点关注 / 一键三连”，整句去掉；其他结尾句保留。
   - 命令、文件名、标识符加行内代码。
   - 引号用 “”，不用「」。
   - YouTube 讲稿另有几条替换（频道话术、“观众”、指着画面的句子），见 references/youtube.md。

   不润色口语，不删句，不加导语、提示块或总结。讲稿里过时的事实（版本号、star 数）也不改，因为要不要加说明、怎么加，由用户决定。

3. **放简介。** 讲稿来自 YouTube 视频时，H1 下面先放视频简介的折叠块，读者要复制链接、跳到某个时刻时展开就行：

   ```bash
   python3 .claude/skills/note/scripts/video_description.py <视频 ID>
   ```

   脚本用 agent-browser 打开视频页，输出 `<ReadMore id="简介" label="简介" title="视频标题">`。简介原样照搬，aff 链接、优惠码、频道推广都保留；截断的链接按页面真实地址补全，视频卡片换成完整标题，时间戳链到对应时刻。
   - 文末照同目录的写法加一行出处：`---`，空一行，再写 `*参考视频：[视频标题](https://www.youtube.com/watch?v=<视频 ID>)*`，标题用脚本输出里的那个。
   - 讲稿里“链接在视频简介”“留意一下简介”这类句子保留，“视频简介”只写“简介”（用户要求），第一次出现时链到简介块：链接在[简介](#简介)。点这个链接会跳到开头并自动展开。

4. **加小标题。** 照 `docs/MCP` 课文的写法，用“主题 + 角度”的实词短语，如“CPython 的不足”“PyPy 的速度与兼容性”“CPython 难以撼动的原因”。
   - 不用叙事型、比喻型标题，也不用“起点 / 方案”这类通用标签。
   - 二级标题控制在十个左右：侧边目录平铺十几个二级标题太长，用户要求过分组。简介有章节时间戳时，二级标题跟着章节走，章节里再用三级标题细分。
   - 讲者口头列举的“首先……二看……三看……”写成有序列表，每条内容照抄。
   - H1 是笔记名，结尾不加收尾标题。

5. **加链接。** 只挂在讲稿本身提到的事物上，而且必须读起来自然。链接是给读者的路标，不是装饰：链接太多会打断阅读，挂在代码上会让行内代码和链接的样式叠在一起，读起来像按钮而不是句子。
   - **链接落在中文短语上，行内代码留在链接外面。** 例如 `inspect` 的[官方文档]、`LOAD_FAST` 对应的 [C 代码]、`BINARY_ADD` 的[实现]、`StopIteration` 这个 [exception]。
   - 不要写 [`dis` 模块]、[`ceval.c` 的 `_PyEval_EvalFrameDefault`] 这种把代码包进链接的形式。句子里找不到合适的词可挂时，宁可不加链接，也不要为了挂链接改写句子。
   - **站内链接**：
     - “之前讲过的 X”“X 以后专门讲”链到对应笔记，用相对路径 `./xxx.md`、`../xxx.md`；
     - 需要跳到某一节时带锚点 `#小标题`，锚点按 github-slugger 规则生成：转小写，空格换成 `-`，去掉标点。例如 “其他 Python 实现” → `#其他-python-实现`。
   - **外部链接**：官方文档、项目主页、讲稿里“我们看这是某某官网给出的……”所指的页面。同一个目标只链一次，不给每个 API 名都配链接。
   - **反向补链**：旧笔记里有“之前的某一篇文章提到过”“以后有机会讲”指向本篇话题的，给那句话加上指向本篇的链接。

6. **放代码、配图、加术语（按需）。**
   - 用户给的代码按讲稿的顺序，放到讲稿提到它的那一段后面，比如“我们看下面这个程序”“这里这个函数”。代码原样保留，不改写。对不上位置的代码，在报告里说明放在了哪里。
   - 讲稿演示了完整、能独立运行的代码时，才加 `run` + `output`。输出用 `python3 xxx.py` 在本地实跑后录入，不加 `-u`：输出面板号称是真实运行结果，凭推断写一旦和读者自己跑的不一样就失去信任；加 `-u` 会让多线程的 print 交错，用户平时不这么跑。讲稿里的数字和实跑结果不一致时，正文按实跑结果改，并在报告里说明。
   - 用户给了同一个程序一步步改动的多个版本时（常见于注释掉的一段段代码），照同目录笔记（如《类装饰器》）改用 `<CodeWalkthrough variant="..." step={n} />`（要 `import`，笔记存成 `.mdx`），最后一个实例加 `nav`：数据写在 `src/data/codeWalkthroughs/<variant>.js`，每步一个完整 `main.py` 快照 + 实跑的 `runs`；讲稿提到“第 N 行”时给该步加 `lines: [[N, N]]`。新变体要同时登记到 `src/data/codeWalkthroughs/index.js` 和 `src/components/ProjectCodeViewer/actions.test.mjs` 的 `supported` 白名单，否则 CI 的组件测试会挂。
   - 讲稿描述的行为只在旧版本 Python 成立时（比如“这里会报错”，新版本已经不报错），先问用户；用户选择保留讲稿的说法时，用 `uv run --no-project --python 3.x` 按旧版本实跑录入，并在那一步后加 `:::info` 说明新版本的行为。
   - 贴 CPython 源码时照已有笔记的写法：`` ```c title="Python/ceval.c" showLineNumbers=起始行 {高亮} ``。
   - 用户要配图时，用 academy-diagram-design 技能画，画法、存放位置照它。挑讲稿里用文字描述结构、流程、对比的段落，一篇两三张。图放在讲到它的那段讲稿后面，讲稿就是引出句，不另加；alt 写一句图的结论，具体数字交给图里的标注。同一件事在引出句、alt、图里说三遍，用户会指出重复。
   - 读者可能卡住的术语可以用 `<Term tip="...">词</Term>`（已全局注册）。
   - 用户没给代码、也没要配图时，这一步只看要不要加术语解释。

7. **自检。** 对新笔记和改过的旧笔记跑：

   ```bash
   node .claude/skills/note/scripts/check_note.mjs <笔记.md>...
   ```

   它按 MDX 编译（没闭合的组件、裸的 `<` 和 `{` 在这里就能报出来），并检查链接文字里有没有行内代码、相对链接和图片的文件在不在、`#锚点` 对不对得上小标题和 `id`。几秒就有结果，不用等 CI；而且 CI 对坏锚点只报 WARNING、照样部署，坏锚点只有这一步拦得住。
   完成标准：输出“没有问题”。

8. **提交并看 CI。** 这台机器不跑 `npm run build`：内存小，构建会被 OOM 杀掉（别的电脑照 AGENTS.md 本地构建就行）。CI 失败时不会部署，所以直接推是安全的。
   - 只 `git add` 这次改动的文件，不用 `git add -A`：工作区里可能有别的没提交的改动。
   - 提交信息用中文，格式如 `docs(python): 新增 CPython 笔记，GIL 笔记补上跳转`，末尾加 Co-Authored-By 尾注。
   - 直接推 `main`。
   - 用 `gh run list --commit "$(git rev-parse HEAD)" -L 1 --json databaseId -q '.[0].databaseId'` 拿这次提交的 run id；刚推完可能还没生成，隔几秒再取。别用 `gh run list -L 1`，它可能拿到上一次的 run，报出假“通过”。
   - `gh run watch <id> --exit-status` 放后台跑，把退出码打印出来：CI 连部署和线上验证要五分钟以上，会超过前台命令的时限。失败时用 `gh run view <id> --log-failed` 查原因（多半是坏链接）。

## 报告

用中文，简洁：
- 改了哪些文件；
- 正文里所有不是照抄的地方，逐条列出（视频→文章的替换、识别错误的修正、加字）；
- 加了哪些小标题、哪些站内和外部链接；
- 讲稿里可能过时、但没改的事实，请用户决定是否加说明；
- YouTube 讲稿再加 references/youtube.md 末尾“报告里多写”那两条；
- CI 结果。
