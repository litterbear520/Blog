# 睡觉时让工作继续跑

前面所有铺垫的回报都在这一章。只要您能放心让一个 Agent 自己验证成果，就可以把难题放心交给它独自推进。保证这一切安全的不是祈祷，而是三件实实在在的东西：可检查的完成条件、隔离的 <Term tip="工作树：同一个 git 仓库再检出一份独立的工作目录，各自一个分支，互不干扰">worktree</Term> 或云端 Agent，以及一份早上起来可以直接审查的 <Term tip="决策日志：Agent 每做一个决定记一行，事后可以审查">decision log</Term>。

![她在门口挥手道晚安，机器人们继续维持工厂运转，其中一个正在 BUILD LOOP ACTIVE 标志下更新 DECISION LOG 墙面看板。](./images/overnight.jpg)

## 先赢得信任，再放手让循环自己跑 {#earn-the-trust-before-the-loop}

一个您还信不过的循环，只会把未经检查的烂摊子越产越快，而且每跑一轮问题都在叠加。放手让它独自跑之前，先确认下面四条都已经满足：

- 您自己亲手做过一遍这类任务，或者全程看过 Agent 做完一遍，知道合格的结果应该长什么样。
- Agent 手里握着您自己会用的那套工具和信号：验证技能、性能剖析器、日志。
- 流程的每个阶段都能证明自己的产出，一旦不达标也能当场叫停。
- 您已经读过几份会话记录，并把反复出现的失误沉淀成了工具、技能或检查项。

这四条全部成立之后，再让循环自主运行。在此之前，先在您盯着的情况下跑。

## 过夜交接的约定 {#the-overnight-contract}

一份好用的过夜交接不需要写得很长，只要包含目标、完成条件、权限边界和退路就够了：

<Tabs groupId="prompt-lang">
<TabItem value="en" label="English">

```text
/poteto-mode im going to bed. migrate every caller to the new parser in a fresh worktree off <base>.
done means zero old callers, all parser fixtures pass, old api deleted.
keep a decision log. don't ask me before committing.
/loop until done. if you're truly stuck after a few hours, stop and write up why.
```

</TabItem>
<TabItem value="zh" label="中文">

```text
/poteto-mode im going to bed. 基于 <base> 新建一个干净的 worktree，把所有调用方都迁移到新的解析器。
完成的定义是：不再有任何旧调用方、所有解析器测试样例全部通过、旧 api 删除干净。
记一份 decision log。提交代码前不用问我。
/loop 一直跑到完成。如果几个小时后确实卡死了，就停下来写清楚卡在哪。
```

</TabItem>
</Tabs>

逐行看一遍，每一句都在为您省去什么麻烦：

- “im going to bed”（我要睡了）会覆盖这段会话里默认的请示习惯，Agent 看到后就不再频繁停下来问您，而是持续推进。
- “done means...”（完成的定义是……）把抽象目标落成了每一轮都能直接跑的检查项。
- “fresh worktree off `<base>`”（基于 `<base>` 新建一个干净的 worktree）把这次运行隔离出来，不会和您手头开着的其他工作互相打架。
- “don't ask me before committing”（提交前别问我）提前把权限批好，免得 Agent 卡在等您确认这一步。
- `/loop` 是 Cursor 内置的唤醒机制，不是 pstack 的技能。[Autonomous run](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autonomous-run.md) <Term tip="剧本：poteto-mode 里一类任务的固定步骤，例如 Bug fix、Feature">playbook</Term> 用它在事件到来时或按固定间隔被唤醒，重新检查完成条件。
- 退路条款允许 Agent 遇到真正的死胡同时停下来并写明原因，这比让它硬撑八个小时、把目标偷偷曲解成别的东西强得多。

因为您要离开一阵再回来验收，`/poteto-mode` 会把任务转交给 [`/figure-it-out`](https://github.com/cursor/plugins/blob/main/pstack/skills/figure-it-out/SKILL.md)。它会在动任何代码之前先规划好整个运行的各个阶段，并把 decision log 接进流程。

如果想中途主动停下，直接告诉 Agent 暂停，或者说您马上要离线、要重启 Cursor。[Pause safely](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/pause-safely.md) playbook 会把当前这一步收尾或回退干净，提交一个中途进度检查点，并写下一份续接说明。回头新开一段对话时，Agent 会通过 Session pickup playbook 读这份说明接着往下做。说“keep going”（继续）绝不会触发暂停。

## 循环整晚都在做什么 {#what-the-loop-does-all-night}

<Diagram variant="pstackOvernightLoop" />

每一轮迭代都只做一件事：改一小步、验一次、记一行日志。没有带来进展的改动会被直接丢弃，不会留在代码里混着。如果遇到瓶颈停滞不前，应该换一条思路，而不是直接停下，更不能偷偷放宽完成条件来宣布胜利。

## 早晨如何审查成果 {#the-morning-audit}

让整晚的工作变得可审查的，是 [`/show-me-your-work`](https://github.com/cursor/plugins/blob/main/pstack/skills/show-me-your-work/SKILL.md)。它把每条决定记成 TSV 文件里的一行，字段包括时间、阶段、决定内容、原因、证据位置和结果，默认存在 `decisions.tsv`（如果多个任务共用一个目录，则存在 `.audit/<task-slug>.tsv`）。这份文件默认留在本地，不进版本库；如果改动足够大、评审人需要看到决策轨迹才敢放心，您再把它提交上去。

早上回来后，让它按审查格式给您汇报整晚的进展：

<Tabs groupId="prompt-lang">
<TabItem value="en" label="English">

```text
/show-me-your-work catch me up on what you did last night
```

</TabItem>
<TabItem value="zh" label="中文">

```text
/show-me-your-work 给我汇报一下你昨晚干了什么
```

</TabItem>
</Tabs>

交回摘要之前，这个技能会另派一个来自不同模型家族的审查者，把决策轨迹和会话记录通读一遍，并在回复末尾加上一段 Attention（重点关注）小节，专门标出最值得您仔细查验的地方。先看这一节，再顺着它指出的日志行去查。您是在审计关键决策，而不是把整晚的记录从头读到尾。

如果您只想要个简短进展而不是正式审计，可以在跑任务的那个对话里直接输入 [`/ketchup`](https://github.com/cursor/plugins/blob/main/pstack/skills/ketchup/SKILL.md)。它只读不改，会用大白话告诉您从您上一条消息到现在发生了哪些变化，并附上过程中生成的截图和小示意图。接着它会列出每一件等您决定的事——比如合并、审批或在几个方案里选一个——同时给出它的推荐、证据和风险，让您光看这一条回复就能做决定。

## 当过夜的不是单个任务，而是一整条队列 {#when-the-night-holds-a-queue-not-a-task}

上面的约定是把一个任务推向一个完成条件。但有些晚上要跑的不止一件事，可能是一排彼此独立的改动，甚至是一项跨多个模块的大工程。有两个 playbook 和一个技能可以把同样的信任机制往上扩展。

[Autopilot-full](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-full.md) 会把一串彼此独立的 PR 一路推进到合并。每个 PR 都分派一个负责的 Agent，从编码一直跟到合并，但没有任何一个负责的 Agent 可以凭自己的判断就点合并。代码就绪后，一组全新的验证者会并发核验这个版本；如果之后只做了 rebase 或小修小补，只需一个全新的验证者复核，只有引入新行为或新增了一大片 <Term tip="这次改动前后的差异">diff</Term> 时，才会重新拉起整组验证者。只有最终要合进去的那个补丁拿到全绿结论，合并才会被放行：

<Tabs groupId="prompt-lang">
<TabItem value="en" label="English">

```text
/poteto-mode full autopilot on this queue. each item is independent. i want them merged by morning.
```

</TabItem>
<TabItem value="zh" label="中文">

```text
/poteto-mode 对这个队列开全自动模式。每一项都彼此独立，我希望明天早上前全都合并掉。
```

</TabItem>
</Tabs>

[Autopilot-stack](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/autopilot-stack.md) 就是去掉自动合并这一步的 Autopilot-full。您早上醒来，看到的是一批已经过验证、各自附带结论的 PR，然后由您亲自过目并合并。只有后一个 PR 确实建立在前一个 PR 之上时，才会把它们叠成前后依赖的链条。如果您希望任何代码进主干前都先经自己的眼，选它而不是 Autopilot-full：

<Tabs groupId="prompt-lang">
<TabItem value="en" label="English">

```text
/poteto-mode autopilot these five changes, but don't merge. i'll land them in the morning.
```

</TabItem>
<TabItem value="zh" label="中文">

```text
/poteto-mode 自动推进这五个改动，但先别合并。我明天早上自己来合。
```

</TabItem>
</Tabs>

如果是跨越许多包的大迁移这类整项工程，并没有对应的固定 playbook。`/poteto-mode` 会把这种规模大、跨模块的任务交给 [`/figure-it-out`](https://github.com/cursor/plugins/blob/main/pstack/skills/figure-it-out/SKILL.md)，由它专门设计一套严谨的运行方案：

<Tabs groupId="prompt-lang">
<TabItem value="en" label="English">

```text
/poteto-mode migrate every package to the new store. own it until each one is converted and merged. i'll check in twice a day.
```

</TabItem>
<TabItem value="zh" label="中文">

```text
/poteto-mode 把所有包都迁移到新的存储层。你全程负责，直到每一个包都改完并合并。我每天会来过问两次。
```

</TabItem>
</Tabs>

## 并行推进多个 Project {#run-many-projects-in-parallel}

[Cursor 的 Project](https://cursor.com/blog/projects) 给一个协调者 Agent 配了一条长期保留的对话线程。协调者自己不写代码，只负责指挥子代理；这些子代理默认跑在云端，所以哪怕您合上笔记本，工作也照样往下走。给协调者发指令时以 `/poteto-mode` 开头，它拉起的子代理就会照着 playbook 执行。每个新启动的 <Term tip="worker：被派去完成其中一份工作的子代理，各管一片、各自汇报">worker</Term> 都会先读 [`worker.md`](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/worker.md)，因此它们会守住开局定下的标准，遇到可逆的决定自己拿主意而不来打扰您，并把 PR 整理到可以直接评审的状态。

有几个小习惯很有帮助：

- 给每一大块独立工作单独建一个 Project，比如一个新功能、一次迁移、一轮性能优化或一次技术债清理。多个 Project 可以同时推进。
- 把相关的对话都拖进这个 Project 里，已经结束的也算。它们会成为 Project 里所有 Agent 共享的上下文。
- 每个 PR 合并前都配一组验证者并行把关，队列就交给 Autopilot-stack 或 Autopilot-full 去推。
- 让协调者拿出一份有数据支撑的计划，并让它用原型先把悬而未决的问题验证清楚，再回来问您。

一条提示词就能把整个 Project 从调研一直带到落地：

<Tabs groupId="prompt-lang">
<TabItem value="en" label="English">

```text
/poteto-mode refactor this repo so its architecture is more agent friendly. use /correct and /architect on past commits and review comments to find the mistakes agents make most here. use /recall for context from past chats. answer open questions with prototypes instead of asking me. come back with a plan backed by real data. once i approve it, run it with autopilot-stack or autopilot-full, and ask me which.
```

</TabItem>
<TabItem value="zh" label="中文">

```text
/poteto-mode 重构这个仓库，让它的架构对 Agent 更友好。用 /correct 和 /architect 分析过去的提交和评审意见，找出 Agent 在这里最常犯的错。用 /recall 翻出历史对话里的上下文。遇到悬而未决的问题，直接做原型验证，别来问我。拿一份有真实数据支撑的计划回来。我批准之后，用 autopilot-stack 或 autopilot-full 跑起来，到时候问我选哪一种。
```

</TabItem>
</Tabs>

## 让循环自己启动 {#let-loops-start-themselves}

前面所有的循环，都还得等您手动发一条消息来启动。换成定时或事件驱动的自动化任务，连这一步都可以省掉。软件维护天然能拆成几个适合自动化的阶段：分诊问题反馈、复现问题、修复问题、验证修复。有两条规矩能让这条流水线始终靠得住：

- 每个阶段都有权叫停整条流水线。分诊阶段可以判定反馈属于预期行为，复现阶段可以确认无法复现，修复阶段也可以判断改动风险太高。这些中止结果都很有价值，因为它们能在进入下一阶段之前就把坏改动拦下来——越往后，撤销的代价越高。
- 每个阶段都带着证据交接。复现阶段附上出错状态的截图和录屏，修复阶段附上修复前后的对比证据。这样人类甚至不用读一行代码，就能先确认 Agent 修的是不是真正的问题。

pstack 内置了这样一套针对 Slack 问题反馈的[自动化任务包](https://github.com/cursor/plugins/blob/main/pstack/automations/benny/README.md)，默认处于休眠状态。其中一个自动化任务负责分诊每条反馈，另一个负责复现已确认的 bug，必要时还会准备一份小规模的修复草稿。想把它搭起来时，只需让 Agent 去读里面的 [`FOR_AGENTS.md`](https://github.com/cursor/plugins/blob/main/pstack/automations/benny/FOR_AGENTS.md)，并指明目标仓库即可。

:::warning[误区]

时间长度不是完成条件。“work on this for 4 hours”（在这个任务上干 4 个小时）没给 Agent 任何可以核验的标准，您早上醒来收获的只是四个小时的瞎忙，而不是想要的结果。交给 `/loop` 的，必须是一个能明确判出“通过”或“失败”的条件。

:::
