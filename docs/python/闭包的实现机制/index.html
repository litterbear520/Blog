闭包的实现机制

在全局和闭包变量中，我们讨论了闭包变量的使用方式。这篇继续看它的实现：外层函数返回后，内层函数为什么还能访问 data？外层重新给 data 赋值时，内层又为什么能读到新的值？

闭包基础​

先看这段代码。函数 f 里定义了一个空列表 data，以及一个使用 data 的内层函数 inner。

def f():
    data = []

    def inner(value):
        data.append(value)
        return data

    return inner

g = f()
print(g(1))
print(g(2))

data 是 f 的局部变量；对 inner 来说，它来自外层函数作用域，既不是自己的局部变量，也不是模块的全局变量。inner 保留了对这个外层绑定的访问，由此形成闭包。

我们可以看到，这个 f 函数运行的结果，是返回这个 inner 函数。我们把这个结果保存给 g，那这个时候 g 跟 inner 都是一样的，是同一个函数。这个 inner 函数有一个参数 value，它每次会把这个 value 加到 data 这个 list 里面，然后把 data 这个 list 返回。

我们简单跑一下，打印一下 g(1)，再打印一下 g(2)。可以看到，g(1) 把 1 加到这个 list 里面，并且打印出来。g(2) 把 2 又加到这个 list 里面，打印出来的是 1、2。也就是说，这两次 g 的调用里，或者说是 inner 的调用里，它们使用的 data 是同一个 data，是 f 里面我们初始化的那个 data。

外层变量重赋值​

一种猜测是：定义 inner 时，把外层变量当前的值复制一份保存下来。我们可以用一次重新赋值检验这个猜测。

在定义完 inner 之后、返回它之前，把 data 重新赋值为 [0]。这会让 data 指向一个新列表，原来的空列表并没有被修改。

def f():
    data = []

    def inner(value):
        data.append(value)
        return data

    data = [0]
    return inner

g = f()
print(g(1))
print(g(2))

第一次调用就得到 [0, 1]，说明 inner 读取的是重新赋值后的 data。闭包保留了对外层变量绑定的访问，并不是保存定义 inner 时的列表快照。

这里还有一个问题：f() 已经执行结束，为什么 g 仍然能访问这个列表？函数返回后，对象是否继续存在，取决于是否还有引用保留它。要解释这个例子，需要找到谁在持有 data。

闭包字节码​

运行版本

本文代码和预录输出使用 CPython 3.13.12。字节码属于 CPython 实现细节，不同版本的指令和显示格式可能不同；例如这里的 SET_FUNCTION_ATTRIBUTE 是 Python 3.13 新增的指令。可对照 Python 官方 dis 文档。

用 dis.dis(f) 查看外层函数和内层函数的字节码。

import dis

def f():
    data = []

    def inner(value):
        data.append(value)
        return data

    return inner

dis.dis(f)

外层函数里出现了 MAKE_CELL、STORE_DEREF 和 SET_FUNCTION_ATTRIBUTE 8 (closure)。内层函数读取 data 时使用 LOAD_DEREF，读取参数 value 时则使用 LOAD_FAST。这两条指令访问的是不同种类的变量。

创建 cell​

MAKE_CELL创建一个 cell 对象，用来保存需要被嵌套作用域共享的变量绑定。 为 data 创建一个 cell 对象。cell 保存对当前值的引用，外层和内层函数通过同一个 cell 访问这个绑定。

更新 cell​

BUILD_LIST 0 创建空列表，随后 STORE_DEREF把一个值写入指定 cell，更新这个 cell 保存的变量绑定。 将列表存入 data 对应的 cell。第二个例子中的 data = [0] 也会更新这个 cell，因此 inner 随后读取到的是新列表。

这里要区分重新赋值和修改对象：data = [0] 改变 cell 指向的对象；data.append(value) 修改已有列表，cell 仍然指向同一个列表。在 inner 中调用 append 不需要 nonlocal；如果要在 inner 中给外层的 data 重新赋值，才需要声明 nonlocal data。

使用 STORE_DEREF 还是 STORE_FAST，由编译器根据变量的作用域决定。data 虽然定义在 f 内，但也被 inner 引用，因此编译器会为它生成通过 cell 访问的指令。

访问 cell​

inner 中的 LOAD_DEREF读取指定 cell 中保存的值，供当前函数使用。 通过 cell 取得列表，然后执行 append 或返回这个列表。

调用 inner 时，开头的 COPY_FREE_VARS把函数闭包中的 cell 引用复制到当前调用帧，供 LOAD_DEREF 等指令访问；不会复制 cell 中的列表。 把函数闭包中的 cell 引用放入当前调用帧。它不复制列表，也不创建独立的 cell，因此多次调用 g 仍然访问同一个绑定。

同一个 data，从两个函数的角度有不同的名称：

所在函数名称含义
fcell variable（co_cellvars）本函数定义、被内层作用域引用的局部变量
innerfree variable（co_freevars）本函数使用、由外层函数作用域提供的变量

闭包属性​

cell 持有列表的引用，那么 f() 返回后，又是谁在持有 cell？

在外层函数的字节码中，LOAD_FAST (data) 取出 cell，BUILD_TUPLE 1 将它放入元组，MAKE_FUNCTION 创建 inner 函数对象。随后 SET_FUNCTION_ATTRIBUTE 8 (closure)将 cell 元组设置为函数对象的闭包属性；参数 8 表示 closure。 将这个元组保存在函数对象上。

执行 g = f() 时，g 引用的是 f 返回的那个 inner 函数对象。它通过 __closure__ 保留 cell，无需保留 f() 的整个调用帧。直接打印这个属性就能看到：

def f():
    data = []

    def inner(value):
        data.append(value)
        return data

    return inner

g = f()
print(g.__closure__)

输出是一个只含一个 cell 的元组；cell at ... 是 cell 自身的地址，list object at ... 是它引用的列表的地址。地址会随运行变化。按照 Python 函数对象文档，这些 cell 与 g.__code__.co_freevars 中的变量名按位置对应。

验证对象引用​

继续保留 __closure__ 输出，再打印 g(3) 返回值的 id。最后补上 cell_contents 和 is，直接检查 cell 保存的内容以及对象身份。

def f():
    data = []

    def inner(value):
        data.append(value)
        return data

    return inner

g = f()
print(g.__closure__)
print(g(1))
print(g(2))
print(hex(id(g(3))))
print(g.__closure__[0].cell_contents)
print(g.__closure__[0].cell_contents is g(4))

十六进制 id 与第一行 list object at ... 的地址一致。这里使用的是 CPython，它的 id 对应对象的内存地址；比较时要看列表地址，而不是 cell 自身的地址。

调用 g(3) 同样执行了 append，所以接着读取 cell_contents 得到 [1, 2, 3]。最后一行的 g(4) 又追加了 4，而 is 结果为 True：返回值与 cell 持有的确实是同一个列表。

这个例子的引用关系是 g → 函数对象 → __closure__ 元组 → cell → 列表。只要这条引用关系仍然保留，列表就可以在 f() 返回之后继续被访问。

与全局变量对比​

把 data 和 inner 移到模块顶层，也可以让多次函数调用使用同一个列表。给这段代码补上调用和 __closure__ 检查：

data = []

def inner(value):
    data.append(value)
    return data

print(inner(1))
print(inner(2))
print(inner.__closure__)

两次调用同样得到 [1] 和 [1, 2]，但 inner.__closure__ 是 None。这里的 data 是模块全局变量，函数通过全局命名空间查找它，读取时使用 LOAD_GLOBAL，没有通过闭包 cell 访问。

闭包中的 data 属于外层函数的一次调用，不属于模块全局作用域。在前面的闭包版本中，每次重新调用 f()，都会创建新的 cell 和列表；同一个返回函数的多次调用才会持续使用那一次创建的绑定。这也解释了为什么 f() 已经返回，g 依然能够不断向自己的列表追加数据。
