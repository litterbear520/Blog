# 循环与第一个工具

一个能聊天的模型，还不能直接回答店里的库存问题。这一课，我们为它接入商品搜索，让它先取得信息，再回答用户。

学完这一课，您将能够区分模型和程序在工具调用中的职责，读懂一次工具请求与结果回传，并解释为什么需要一个循环。开始前，只需能用 Python 完成一次 Messages API 请求；文末的完整演练也保留了这个起点。

## 只会聊天的模型

假设您正在为一家商店编写购物助手。用户问：

> 我想找耳机，店里有吗？

模型可以介绍耳机，却无法仅凭已有知识确认这家店的商品和库存。我们需要给它一个查询商品目录的途径，而不是让它猜测。

在这个例子里，工具调用分成三个动作：**模型提出搜索请求，程序执行搜索，模型根据结果回答。** 模型并不会直接运行我们电脑上的 Python 函数。

下面始终使用“找耳机”这个例子。我们先让 Python 能搜索，再告诉模型如何请求这项能力。

## 定义一个搜索工具

### 先让 Python 能搜索

为了专注于工具调用，我们先用内存中的 `PRODUCTS` 列表代替数据库。列表里存放商品名称、价格和库存状态，搜索函数只做关键词匹配：

<CodeBlock language="python" title="搜索函数（节选）">{snippets.search}</CodeBlock>

调用 `search_products("耳机")`，就会从列表里找出名称包含“耳机”的商品，再把结果序列化为 JSON 字符串。到这里，它仍然只是一个普通的 Python 函数，与模型无关。

### 告诉模型怎么使用它

接下来，我们用工具 Schema 描述这个函数。模型会看到这份说明，而不是自动看到函数体：

<CodeBlock language="python" title="工具定义">{snippets.schema}</CodeBlock>

`name` 用来标识工具，`description` 说明什么时候、怎样使用它，`input_schema` 则描述参数。这里的 `query` 是必填关键词，`limit` 是可选的结果数量。

例如，看到“我想找耳机”，模型可以据此请求 `search_products`，并把 `query` 设为“耳机”。**Schema 描述的是调用方式，搜索工作仍由刚才的函数完成。**

## 执行请求，再把结果送回去

我们把工具定义放进请求的 `tools` 参数，让模型在回答时可以选择使用它：

<CodeBlock language="python" title="发送消息与工具定义（节选）">{snippets.request}</CodeBlock>

当模型需要搜索时，回复中会包含 `tool_use` 块，给出工具名称、参数和这次调用的 ID。回复也可能同时包含文字，因此程序要检查内容块，不能只读取第一段文本。

程序先把模型的整条回复作为 `assistant` 消息保留在 `messages` 中，再执行其中的工具调用。`TOOL_MAP` 是工具名到 Python 函数的映射：

<CodeBlock language="python" title="执行工具并追加结果（节选）">{snippets.results}</CodeBlock>

这里最重要的不是打印输出，而是构造 `tool_result`。其中的 `tool_use_id` 必须与对应调用的 `block.id` 相同，模型才能把结果与请求对上。

这些结果通过一条 `user` 消息送回模型。这里的 `user` 是 API 的消息角色，并不表示用户又手动输入了一句话。下一次请求会带上原始问题、模型提出的调用，以及程序取得的搜索结果。

## 循环的工作原理

搜索完成以后，模型还需要读到结果，才能组织回答；它也可能发现信息不足，再请求一次工具。因此，我们重复“请求模型—执行工具—回传结果”，直到这一轮回答结束。

`stop_reason` 告诉我们模型为什么停下：`tool_use` 表示需要执行工具并继续，`end_turn` 表示本轮正常结束。当前示例用下面的判断决定是否继续工具调用：

<CodeBlock language="python" title="是否继续调用（节选）">{snippets.stop}</CodeBlock>

这是一个最小实现：它遇到非 `tool_use` 的情况都会退出。实际应用还要区分 `max_tokens` 等其他停止原因，不能把“退出循环”都当成“正常完成”。

完整脚本有两层循环：内层完成当前问题所需的工具调用，外层等待用户的下一句话。外层不清空 `messages`，所以用户接着追问时，之前的对话仍会一起交给模型。
