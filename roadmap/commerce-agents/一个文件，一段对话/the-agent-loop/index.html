循环与第一个工具

工具让模型能够取得对话之外的信息。以购物助手为例，我们可以提供一个商品搜索工具，让模型先查询商品目录，再根据结果回答用户。

为什么需要工具​

假设用户问：“店里有没有降噪耳机？”模型可以介绍降噪耳机，却无法仅凭已有知识确认这家店的商品和库存。要回答这个问题，它需要取得商店的数据。

我们可以让程序查询商品目录，再把结果交给模型。这里有一个重要的分工：模型决定需要查询什么，程序负责执行查询，模型再根据结果回答。 模型发出工具调用请求，并不代表 Python 函数已经执行。

定义商品搜索​

先为程序准备一个普通的 Python 函数。为了专注于工具调用，我们用内存中的 PRODUCTS 列表代替数据库，按商品名称匹配关键词：

搜索函数（节选）
def search_products(query: str, limit: int = 5) -> str:
    """在假商品列表里做简单的关键词匹配，返回 JSON 字符串。"""
    query_lower = query.lower()
    results = [p for p in PRODUCTS if query_lower in p["title"].lower()]
    results = results[:limit]
    return json.dumps(results, ensure_ascii=False)

调用 search_products("耳机")，就会找到名称中包含“耳机”的商品，并把结果转换为 JSON 字符串。此时，搜索已经能在 Python 中独立工作，但模型还不知道怎样请求它。

我们还需要一份工具定义，也就是 Schema。它通过 name 标识工具，通过 description 说明用途，再用 input_schema 描述参数。在这个例子中，query 是必填的关键词，limit 是可选的结果数量。

查看搜索工具的定义
工具 Schema
search_products_schema = {
    "name": "search_products",
    "description": (
        "搜索商品目录，返回商品的 id、标题、价格、评分和库存状态。"
        "用具体的关键词搜索。"
        "顾客提到多个不同商品时，每个商品单独搜一次。"
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "要搜索的关键词。",
            },
            "limit": {
                "type": "integer",
                "description": "最多返回几条结果。",
            },
        },
        "required": ["query"],
        "additionalProperties": False,
    },
}

把这份定义放进请求的 tools=[search_products_schema] 后，模型就可以提出搜索请求。例如，针对用户的问题，它可以选择 search_products，并提供参数 {"query": "耳机"}。工具定义描述调用方式，函数负责实际搜索。

执行工具并返回结果​

模型需要搜索时，回复中会出现 tool_use 内容块，包含工具名称、参数和调用 ID。程序先把完整的 response.content 作为 assistant 消息追加到 messages，再处理其中的工具调用。

下面的代码用 TOOL_MAP 按名称找到搜索函数，执行后把结果包装成 tool_result：

执行工具并追加结果（节选）
tool_results = []
for block in response.content:
    if block.type == "tool_use":
        print(f"[调用工具] {block.name}({block.input})")
        run = TOOL_MAP[block.name]
        output = run(**block.input)  # type: ignore[arg-type]
        print(f"[工具结果] {output}")
        tool_results.append(
            {
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            }
        )
messages.append({"role": "user", "content": tool_results})

tool_use_id 对应这次请求的 block.id，用来说明“这是哪一次调用的结果”，而不是搜索到的商品 ID。结果放在一条 user 消息中；这里的 user 是 Messages API 的角色，并不表示用户又输入了一句话。

只有把这些消息带入下一次模型请求，模型才能读到搜索结果。仅在终端打印结果，并不会把数据交给模型。

为什么需要循环​

第一次请求让模型提出搜索，下一次请求才让它读到结果。如果信息还不够，模型也可以继续请求工具。因此，程序需要重复“请求模型—执行工具—回传结果”，而不是调用一次 API 就结束。

模型回复中的 stop_reason 用来区分这些情况：tool_use 表示需要执行工具并继续；end_turn 表示当前这一轮回答正常结束。示例中的内层循环用下面的条件决定是否继续：

循环中的判断（节选）
if response.stop_reason != "tool_use":
    break

这段最小实现遇到非 tool_use 的情况都会退出；实际应用还需要单独处理 max_tokens 等停止原因，不能把退出都当成正常完成。

查看完整代码与运行方式

下面的演练默认定位到完整循环，也可以回看搜索函数和工具定义。正文中的代码节选来自同一份快照。

第 5 步 · 两层 while5 / 5

外层 while 负责等待用户输入，遇到空输入就退出。内层 while 才是 agent 循环的本体：调用模型，把 assistant 的回复整个追加进 messages；如果 stop_reason 不是 tool_use 就跳出；否则执行每一个 tool_use 块，把 tool_result 打包成一条 user 消息追加进去，然后再循环一次。

有一个细节需要注意：assistant 的 response.content 要原样追加，包括其中的 tool_use 块；下一条 user 消息里的 tool_use_id 必须与之对应，模型才知道哪个结果属于哪次调用。

这就是购物助手的基本循环：模型提出工具请求，程序执行并送回结果，模型继续回答。以后加入商品详情和购物车时，我们仍会沿用这个过程，只是让模型可以选择更多工具。
