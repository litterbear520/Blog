循环与第一个工具

一个购物助手不能只会介绍商品，还要能查询商店里实际有什么。这一节，我们从“店里有没有降噪耳机？”这个问题出发，为助手接上一个商品搜索工具，再把搜索结果交回模型，让它完成回答。

读完这一节，您将能够区分工具定义与工具函数，跟踪一次 tool_use 到 tool_result 的过程，并解释为什么一次工具调用通常需要不止一次模型请求。阅读代码只需要了解 Python 函数、字典、循环和 JSON；运行示例时才需要准备 API 密钥。

只会聊天还不够​

模型知道什么是降噪耳机，不代表它知道这家店的商品目录。即使我们在提示词里写“你是一个购物助手”，也没有把商品的价格、评分和库存状态交给它。

我们需要让程序提供一项具体能力：根据关键词搜索商品。为了先看清调用过程，这里用六条示例商品组成的 PRODUCTS 列表代替数据库。它不是实时库存服务，但足以演示模型怎样取得原本不在对话中的信息。

这里的分工是：模型提出搜索请求，Python 程序执行搜索，模型再根据搜索结果回答。 模型生成了工具调用，并不等于函数已经执行。

一次搜索怎样完成​

工具调用不是模型直接进入 Python 程序，而是应用与模型之间的一次往返。以查找耳机为例，这个过程可以分成四步：

  1. 程序把用户问题和搜索工具的定义一起发给模型，说明有哪些工具、各自接受什么参数。
  2. 模型需要商品数据时，返回一个 tool_use 内容块，其中包含工具名称、输入参数和这次调用的 ID。
  3. 程序执行对应的搜索函数，把结果放进 tool_result 内容块，并用 tool_use_id 对应这次调用。
  4. 程序带着更新后的对话再次请求模型。模型读到结果后，可以回答用户，也可以继续请求工具。

因此，搜索后还要再请求一次模型：函数的返回值只有被加入对话并发送出去，模型才能看到。 只把结果打印在终端里，并没有完成回传。

逐步查看代码​

下面只看一个完整的 agent.py，不在多个代码片段之间来回切换。步骤按“准备搜索能力 → 交给模型 → 执行与回传 → 继续或结束”的顺序展开；教学顺序不必与文件中的定义顺序相同。

点击“下一步”会展开对应说明，打开文件并滚动到高亮的代码。也可以直接点击某个步骤回看，或在代码区自由阅读。这里是代码阅读演练，不会发送 API 请求。

教程步骤

让我们通过一个示例项目来更好地了解如何实现此功能。

我们先准备一个商品目录。PRODUCTS 中的每条记录都包含商品 ID、名称、价格、评分和库存状态。例如，降噪耳机是一条在库商品，咖啡机则标记为缺货。

这六条数据放在 Python 程序里，并没有自动进入模型的上下文。接下来，我们会提供一个函数，让程序按模型请求取出相关记录，而不是把整个目录直接写进提示词。

search_products 是一个普通的 Python 函数。它把 query 转为小写，在商品名称中做包含匹配，再用 limit 限制结果数量，最后通过 json.dumps 返回 JSON 字符串。

例如，search_products("耳机") 会返回名称中包含“耳机”的记录；没有匹配项时返回字符串 "[]"。这里没有向量检索或模型推理，搜索本身完全由 Python 完成。

函数能够执行搜索，还需要让模型知道如何请求它。工具定义通过 name 标识 search_products，通过 description 说明用途，再用 input_schema 描述参数。

query 是必填的字符串，limit 是可选的整数。模型省略 limit 时，最终执行的 Python 函数会使用默认值 5。这份定义描述调用方式，不会把函数实现发送给模型，也不会自动执行函数。

外层循环读入用户的问题，把它追加为 user 消息。接着，内层循环通过 client.messages.create 发出请求：messages 是当前对话，tools=[search_products_schema] 告诉模型可以使用这个搜索工具。

对于“店里有没有降噪耳机？”，模型可以返回 search_products 的调用请求，例如参数为 {"query": "耳机"}。这仍然只是一份请求，程序还没有执行搜索。

response.content 是内容块列表，不一定只有一段文字。它可以同时包含 text 和 tool_use；tool_use 中的 name、input 和 id 分别说明调用哪个工具、使用什么参数，以及这次调用的标识。

程序把完整的 response.content 作为 assistant 消息保存，再把 text 内容打印出来。不能只保存打印出的文字，否则下一次请求中会缺少工具请求，后面的结果就没有对应对象。

模型需要工具时，程序遍历回复中的 tool_use 内容块。TOOL_MAP 把工具名称映射到真正的 Python 函数，run = TOOL_MAP[block.name] 先找到它，run(**block.input) 再把参数展开并执行。

当输入是 {"query": "耳机"} 时，这相当于调用 search_products(query="耳机")。直到执行这一行，搜索才真正发生。遍历内容块也允许程序处理同一条回复里的多个工具请求。

程序把每个函数返回值包装成 tool_result。content 保存搜索结果，tool_use_id 使用刚才的 block.id，表示“这是哪一次调用的结果”，不是搜索到的商品 ID。

这些结果被放进一条 user 消息，紧接着之前的 assistant 工具请求。这里的 user 是 API 消息角色，不是等待用户重新输入。追加完成后，内层循环回到顶部，带着更新后的 messages 再次请求模型；打印 [工具结果] 本身并没有把数据发送出去。

每次模型响应后，程序都会检查 stop_reason。等于 tool_use 时，这个 break 不会执行，程序继续处理工具；搜索结果回传后的下一次响应，也会经过同一处判断。

当模型以 end_turn 正常结束回答时，程序退出内层循环，回到外层等待用户继续说话。当前最小代码对所有非 tool_use 都执行 break，所以 max_tokens 等情况也会退出，不能把它们误认为正常完成。

把一次调用放回整段对话​

看过演练后，再从消息的角度看一次往返。下面是“一次搜索后直接回答”的结构示意，不是预录运行结果；真实模型可以请求不同参数，也可以发起多次搜索。

顺序消息角色消息内容
1user用户问：“店里有没有降噪耳机？”
2assistant模型提出 search_products 调用，例如参数为 {"query": "耳机"}。
3user程序送回包含搜索结果的 tool_result，对应上一条调用的 ID。
4assistant模型根据商品数据组织回答。

第三条消息虽然使用 user 角色，却不是让用户再输入一次，而是程序按 Messages API 的格式提交工具结果。第二条消息也不能只保留可读文本：模型发出的工具请求必须留在对话中，后面的结果才有对应对象。

代码中的两个循环处理的是两件事。外层循环等待用户的下一句话；内层循环完成当前这句话引发的模型请求和工具调用。 messages 在外层循环之前创建，所以后续追问仍然保留前面的对话。

这里的最小实现把所有非 tool_use 的停止原因都当作退出内层循环的条件，但退出不一定表示回答正常完成。end_turn 表示当前模型回合正常结束，max_tokens 则可能意味着内容被截断；后续完善程序时，还需要分别处理这些情况，并为工具执行增加参数校验、错误处理和调用次数上限。

在本地运行​

通过代码区右上角的复制按钮取得完整代码，保存为 agent.py。在已激活的 Python 虚拟环境中安装依赖：

python -m pip install anthropic python-dotenv

这个代码快照配置的是 DeepSeek 的 Anthropic 兼容接口，不是 Anthropic 官方服务。在 agent.py 同目录新建 .env，把占位文字替换为该服务的密钥；不要把 .env 或真实密钥提交到仓库。

.env
ANTHROPIC_API_KEY=替换为该服务的密钥

SDK 的包名不决定实际请求哪家服务，代码中的 base_url 才决定请求地址。运行前请核对快照中的接口地址和 model 是否适用于您的账户；换用其他服务时，密钥、接口地址和模型名需要一起调整。

python agent.py

出现 >> 后，输入“店里有没有降噪耳机？”。观察终端中的 [调用工具] 和 [工具结果]：前者表示程序准备执行模型请求的搜索，后者是 Python 函数的返回值。模型读到结果后的回答会以 AI: 开头；它也可能在请求工具前先输出一段文字，所以看到 AI: 并不代表整个流程已经结束。

在 >> 后直接按回车可以结束对话。这里只关注请求、执行、回传这条链路，不要求模型每次使用相同措辞，也不要求每个问题都调用工具。

至此，我们已经有了一个能够查询商品并继续对话的助手。以后增加商品详情或购物车能力时，仍然沿用同一条循环：让模型提出请求，由程序执行，再把结果交回对话。
