循环与第一个工具

最小的购物 agent 是一个循环：调用模型、执行工具、把结果送回去。

只会聊天的模型​

我们从一个空目录开始：建一个 venv，pip install anthropic python-dotenv。第一版脚本只做一件事：把一句话发给模型，再把模型的回复打印出来。

此时模型已经可以对话，但它对商品目录一无所知。当您问“有没有耳机”时，它只能凭训练数据编造一个答案。要解决这个问题，我们需要做两件事：给模型一个能查询商品目录的工具，然后加一个循环。当模型表示要使用工具时，我们先执行工具，把结果送回给模型，再让它继续回答。

整个循环由一个信号控制，就是模型回复里的 stop_reason：

stop_reason含义循环做什么
tool_use模型想调用工具执行每一个 tool_use 块，把 tool_result 追加进 messages，再调用一次模型
end_turn模型已经说完打印文本，回到外层循环等待下一句

需要注意的是，messages 从头到尾只有一份，两层循环都往里追加。这意味着模型每次看到的都是完整的对话，包括它自己发出的 tool_use 和我们送回去的 tool_result。

第 1 步 · 第一次 API 调用1 / 5

我们先写一个最简单的脚本：用 Anthropic() 创建客户端，调用 messages.create() 发送一句系统提示词和一条用户消息，然后把回复里的 text 块打印出来。这里没有工具，也没有循环，模型只能聊天。

这个脚本走的是 DeepSeek 的 Anthropic 兼容接口，所以 base_url 和 model 填的是 DeepSeek 的值。如果换回官方接口，只需要删掉 base_url 并改模型名。

为什么这样设计​

为什么不从 LangChain、CrewAI 这些框架开始？ 这是规则 1“一个模型拥有对话”的体现。框架提供的路由和编排在这个项目里是多余的中间层。直接调用 API，我们才能完全控制发给模型的每一个字节，后面做缓存断点、围栏和门控时，都要依赖这种控制权。

工具的 JSON Schema 不是随便写的。 模型看不到函数体，只能看到 schema，所以每个字段的 description 实际上就是给模型的指令。search_products 的 description 告诉模型什么时候该搜、怎么搜、遇到多个商品时要分开搜。一条规则应该放在工具描述、系统提示词还是技能里，取决于它被用到的频率，架构指南中“按频率决定”一节讨论的正是这个取舍。

为什么外层循环不清空 messages？ 当用户接着说“便宜点的呢”时，模型需要知道说的是耳机。保留 messages 的代价是上下文会越聊越长，而且每一轮都要全量重发。后面讲到提示词缓存时会处理这个问题。

现在我们的 agent 能搜索了，但还不能查看商品详情，也不能加入购物车，而且模型有时会编造出不存在的商品 ID。下一课我们先加更多工具，再来处理这第一个 bug。
