# 写给模型的工具结果

工具返回的内容会原样进入模型的上下文，模型下一步做什么，取决于它在结果里读到了什么。一段冗长的 JSON 会挤占上下文，一个笼统的错误码会让模型无从下手。所以参考实现把工具结果当成写给模型的一段话来设计：只留推理要用的字段，在结果里写明下一步，失败时也给一句能照着做的话。

上一课我们跟着一次搜索，走到执行器把结果交回模型为止。这一课接着看回程：同一个结果怎样分给模型和界面，搜索结果为什么要多一行说明，以及五种失败各自变成了一句什么话。

读完这一节，您将能够说出一个工具结果里哪些内容给模型、哪些给界面，判断一个字段该不该进结果，并为一次失败写出模型能照着做的提示。

## 工具结果的两个读者

我们先看一次成功的加购。顾客说“就要这顶帐篷，加一顶”，模型调用 `add_to_cart` 加入 `p-100`。这次调用的结果要交给两个读者，而它们要的东西完全不同：

- **模型**只需要确认发生了什么，好接着和顾客说话。它收到的是一句话：“已加购 p-100 x1。购物车现有 1 件商品，小计 149.00 USD。”
- **界面**要把购物车画出来，需要每一行的标题、单价、件数和小计。它收到的是一个 `cart_update` 事件，里面是完整的购物车。

参考实现用一个类型装下这两份内容：执行器每次返回一个 `ToolOutcome`，`result_text` 进模型的上下文，`events` 交给界面渲染：

这样分开之后，给界面的数据可以很完整，而不必担心挤占模型的上下文。确认里还有一个细节：它只写商品 id，不写商品标题。代码注释说，标题是商品目录里的文本，要留在围栏里，原因在《第三方文本的围栏》一课细讲。`ToolOutcome` 另外两个字段记下调用的结局：`is_error` 标记失败，`blocked` 记下拦住这次调用的门控名，下一课会用到它。

## 只留推理要用的字段

给模型的结果里，每个字段都要回答一个问题：模型推理时用得上吗？用不上的，就不进上下文。搜索结果里的每条商品都经过 `compact_product`：它只挑 14 个字段，`image_url` 和 `category` 不在其中，值为空的字段也去掉。商务指南说过，最常见的冗余就是每条搜索结果都带着一个图片 URL；图片要显示在界面上，那是界面那一路的事。

有选项的商品省得更多。原型店铺的睡垫 `p-400` 有常规款和长款两个变体，详情里的每个变体都经过 `variant_row`，只保留 id、选项值、价格、库存，以及和家族不同的字段。长款 `p-400-l` 前后是这样的：

| 写法 | `p-400-l` 在结果里的样子 |
| ---- | ---- |
| 完整记录 | `{"product_id": "p-400-l", "title": "Trail 自充气睡垫", "price": 69.0, "currency": "USD", "labels": [], "attributes": {}, "in_stock": false, "options": {}, "option_values": {"length": "long"}, "variant_of": "p-400"}` |
| 变体行 | `{"product_id": "p-400-l", "option_values": {"length": "long"}, "price": 69.0, "in_stock": false}` |

整条 `p-400` 的详情数据因此从 759 个字符减到 419 个。标题、币种和所属的家族并没有丢：它们在家族那一层已经出现过一次。

## 在结果里写下一步

光看数据看不出下一步该做什么时，就在结果里附一句下一步，搜索结果是最典型的例子。顾客问“有双人帐篷吗？”，模型用“双人帐篷”去搜。原型店铺里的帐篷叫“双人徒步帐篷”，关键词匹配不上，搜索返回零条。模型实际收到的结果是：

```text
搜索返回 0 条结果：目录中没有匹配此查询的商品。在告知顾客没有该商品之前，先用更宽泛的关键词重试一次，不要把其他商品当作顾客要找的那个。搜索匹配的是商品文本而非 id；要解析商品 id 请用 get_product_details。
<storefront_data>
{"query": "双人帐篷", "result_count": 0, "results": []}
</storefront_data>
```

第一行说明替模型挡住了两个常见的错误：把零结果当成“店里没有”直接告诉顾客，以及拿别的商品冒充顾客要的那个。模型照着说明放宽关键词，改搜“帐篷”，就能找到 `p-100`。说明的最后一句还点破了一个容易踩的坑：搜索匹配的是商品文本而不是 id，要按 id 查商品，得用 `get_product_details`。

有结果时，第一行换成另一句说明：这只是最接近的文本匹配，只有标题和属性都匹配，才算顾客要的商品。这一行放在围栏外面，是整个结果里唯一由运行时生成的文字，除了结果数量，每次都一样。系统提示词里也有对应的规则：说店里没有某样东西之前，要先在这一轮搜两次。

## 失败也写成指令

工具失败时更要这样做。商务指南举过一个例子：与其返回一个笼统的 403，不如返回“查询库存时请带上商品 ID”。购物 Agent 的 `execute` 从不抛异常，每种失败都变成一句带着下一步的话。下面是在原型店铺里实跑出来的原话，其中缺货、不提供和故障三行，是让后端抛出对应的异常得到的：

| 情况 | 谁发现的 | 模型收到的话 |
| ---- | ---- | ---- |
| 参数不合要求 | `parse_argument` 校验 `filters` | “search_products 的参数无效——sort: Input should be 'relevance', 'price_asc', 'price_desc' or 'rating'。调整后再调用一次。” |
| 商品买不了 | 后端抛出 `Unavailable` | “未加入购物车：p-300 缺货。告知顾客，推荐消息中提到的有货替代品，只有顾客选择后才加入。” |
| 本店不提供 | 后端抛出 `NotOffered` | “送货上门不是本店提供的，请直接告知顾客。” |
| 工具出故障 | 其他任何异常 | “search_policies 暂时不可用。用已有的信息继续，或者告诉顾客。” |
| 部署没开这个系统 | `dispatch` 查到工具被关掉 | “get_orders 不是本店提供的功能；直接说明，不要推荐它。” |

每一句都以下一步收尾，而且下一步各不相同：参数错了，改了再调；商品买不了，推荐替代品，但要等顾客选；不提供的服务，直接说；工具故障，用手上的信息继续。“不是本店提供的”和“暂时不可用”也被刻意分开：前者是事实，模型该直接告诉顾客；后者是故障，模型可以绕过它继续工作。工具出故障时，执行器还会记一条带异常栈的日志：异常栈给工程师看，模型只看那一句话。

## 这样写结果的代价

把结果写给模型，可以省掉很多白跑的轮次，但会带来显著的权衡：**每个结果都多了字** —— 有结果时第一行说明有 90 个字符，零结果时有 117 个，每次搜索都要为它付 token；措辞也成了要维护的东西，测试里断言了其中的关键词，比如“暂时不可用”“不是本店提供的”，改措辞时要跟着改测试。不过，有一个好处：结果的格式由同一组函数统一构建，文档字符串写明是为了让每条路径返回相同的字节。按参考实现的设计，Messages API、Agent SDK 和 MCP 三条路径拿到的结果一模一样，这正是规则 6 的要求。

在以下情况下，在结果里加一句下一步：

- 光看数据容易误读，比如零结果，或者文本匹配和按 id 查询的区别；
- 失败有好几种，而每种的正确反应不同；
- 结果交给顾客之前，模型还得先做一个判断，比如缺货时先推荐、等顾客选。

数据本身已经说明一切时，就不必再加话。`get_orders` 有订单时直接返回订单，一张都没有时才附一句“没有找到订单。”；多一句话，就多一份要维护的措辞。

结果写清楚了，模型就知道下一步该做什么。但有一类调用，我们不能只靠模型读懂结果再自觉照做：它们会改动购物车。下一课我们看执行器怎样在写入之前把关。
