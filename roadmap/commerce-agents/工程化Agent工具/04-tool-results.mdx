# 写给模型的工具结果

<LessonMeta lesson={4} minutes={5} />

写工具时，一种很自然的做法是把后端交回的数据原样转给模型：给得越全，模型知道得越多，对吗？并非总是如此。工具结果会原样进入模型的上下文，模型下一步做什么，取决于它在结果里读到了什么。

## 工具结果的两个读者

顾客看完搜索结果里那顶双人徒步帐篷，说：“就要这顶，加一顶。”模型调用加购工具，后端加好以后交回整个购物车。这次调用的产出要交给两个读者：

<Diagram variant="toolResultReaders" />

- **界面：** 要把购物车画出来，需要每一行的商品名、单价、件数和小计。它收到一个购物车更新事件（`cart_update`），里面是完整的购物车。
- **模型：** 只需要知道发生了什么，好接着和顾客说话。它收到一句确认：加了哪件、几件，购物车现在有几件商品、小计多少。

<Term tip="Agent 里负责执行工具调用的那部分代码：收到模型的调用，检查、整理参数，再交给商店的系统">执行器</Term>交回的每个结果都留着这两个位置。那句确认作为工具结果进入对话，事件只发给界面，不进模型的上下文。

所以给界面的数据可以写得很完整，不必担心挤占模型的上下文。

## 工具结果里留哪些字段

写给模型的结果里，每个字段都要回答同一个问题：模型推理时用得上吗？搜索交回那顶双人徒步帐篷时，后端的记录有十几个字段：

<Diagram variant="toolResultFields" />

商品名、价格、评分、库存和属性，模型比较和推荐时都用得上，留下。商品分类和图片地址，模型推理时用不上；空着的字段什么也没说。这几项都不写进结果。

有选项的商品还能再省。同一款商品的几个变体各写一行，每行只有 id、选项值、价格和库存，再加上和这款商品不同的几项。名称、品牌这些相同的字段，只在这款商品那一层写一次。

## 工具结果里的一句说明

有些结果光看数据，模型容易读错。

顾客问“有没有 200 美元以内的双人帐篷？”，模型就用“双人帐篷”去搜。店里那顶叫“双人徒步帐篷”，关键词对不上，搜索返回零条：

<MessageFlow variant="toolResultEmptySearch" />

零条结果最容易被读成“店里没有”。所以结果在数据前面附了一行说明：告诉顾客没有之前，先用更宽泛的关键词再搜一次，也不要拿别的商品冒充。模型照做，改搜“帐篷”，找到了那顶帐篷。

有结果时，这一行换成另一句：搜到的只是最接近的文本匹配，标题和属性都对得上，才算顾客要的那件。

这一行每次搜索都要多占一些 token，措辞也成了要维护的东西。数据本身已经说明一切时，就不必再加话。

:::important[关键要点]
工具结果是写给模型读的一段话，不是后端数据的原样转发：只留推理要用的字段，界面要的数据另走事件，看不出下一步时附一句说明。
:::

回到开头的问题：给得越全，模型未必知道得越多；写对了，它才知道下一步做什么。调用失败时更是如此，这是下一课的内容。
