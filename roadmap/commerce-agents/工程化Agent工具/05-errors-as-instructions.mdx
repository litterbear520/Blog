# 失败也写成指令

<LessonMeta lesson={5} minutes={5} />

顾客说：“就要那款保暖睡袋，加一个。”睡袋已经卖完，后端拒绝了这次加购。如果模型只收到一句“加购失败”，它多半只能回答：“抱歉，出了点问题，请稍后再试。”

## 只报失败为什么不够

结果里只写失败时，对话是这样的：

<Diagram variant="toolErrorBare" />

这句回答帮不上顾客。睡袋并不是暂时出了故障，而是卖完了，过一会儿再试也没用。正确的下一步是告诉顾客，推荐有货的替代品，等顾客自己选。

可模型读不出这些，它手里只有“失败”两个字。失败的原因不同，正确的下一步也不同，而模型只看得到结果里的那段话。所以分辨原因、写出下一步，都要在<Term tip="Agent 里负责执行工具调用的那部分代码：收到模型的调用，检查、整理参数，再交给商店的系统">执行器</Term>里做好。

## 失败怎样变成一句指令

所有工具调用都从执行器的同一个入口（`execute`）进来。这个入口从不让异常打断对话，而是把每次失败写成一句以下一步收尾的话：

1. 参数没通过校验：结果点出哪个字段错了，请模型改了再调。
2. 后端发出“商品买不了”“本店不提供”这类信号：执行器换成店铺事先写好的一句指令。
3. 其他任何异常：完整的异常栈记进日志，留给工程师；模型只收到“这个工具暂时不可用”和接下来怎么办。

睡袋那次加购走的是第二条。先想一想，交回模型的结果该怎么写：

## 每种失败的下一步

每种失败都以一个下一步收尾，而且各不相同：

- **参数不合要求：** 告诉模型哪个字段错了，改了再调。
- **商品买不了：** 请模型告诉顾客，推荐有货的替代品，等顾客自己选。
- **本店不提供：** 请模型直接告诉顾客。这家店没开的功能，比如订单查询，也这样说明。
- **工具出故障：** 请模型用手上已有的信息继续，或者告诉顾客。

“本店不提供”和“暂时不可用”被刻意分开。前者是事实，模型该直接告诉顾客；后者是故障，模型可以绕过它，用手上已有的信息接着工作。

## 被拦下的调用

有些调用没有出错，只是被执行器拦了下来。比如模型拿一个这次会话里没查到过的商品 id 去加购。这不算模型做错了事，所以结果不标成失败，而是写明怎样恢复：先用这个 id 查商品详情，或者通过搜索找到它，再用查到的 id 加购。

有选项的商品没选好时也一样。结果请模型先按顾客的要求确定选项，拿不准就问顾客一次，再用对应变体的 id 加购。

## 回顾

工具失败时，执行器不抛出异常，而是交回一句话：先说发生了什么，再说下一步。异常栈留在日志里给工程师，模型只读那句话。

参数错了，改了再调；商品买不了，先告诉顾客，等顾客选；本店不提供，直接说；工具出故障，绕过它继续；被拦下的调用，照着结果里的步骤恢复。

别只告诉模型出了错，告诉它下一步做什么。
