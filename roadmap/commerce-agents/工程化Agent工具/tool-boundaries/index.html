工具边界

工具把商店已有的系统接给模型。模型只决定搜什么，检索、排序和校验都留在系统一侧。这条分工线就是工具边界。

工具边界解决的问题​

假设顾客问：“有没有 200 美元以内的双人帐篷？”Agent 得先找出帐篷，再去掉超预算的。您有两个选择：

选项 1： 把整个目录放进上下文，让模型自己筛。几件商品时可行，但真实商店的目录放不进上下文，模型也看不到商店的排序信号。

选项 2： 给模型一个搜索工具。模型只决定搜什么，找商品、排顺序交给商店自己的搜索系统。

工具边界的工作原理​

一次搜索是这样穿过工具边界的：

  1. 模型读完工具定义，调用搜索工具（search_products），关键词是“帐篷”，价格上限 200 美元。
  2. 执行器Agent 里负责执行工具调用的那部分代码：收到模型的调用，检查、整理参数，再交给商店的系统收到调用，先整理参数：清洗关键词，校验筛选条件，把条数限制在上限以内。
  3. 商店的后端按自己的逻辑检索、过滤和排序，交回那顶双人徒步帐篷。
  4. 执行器记下这次会话见过的商品，再把结果连同一行说明交回模型。
  5. 模型读完结果，决定向顾客推荐什么、怎么说。

工具边界的优势​

  • 目录多大都行： 模型只读搜索交回的几件商品，不必读整个目录。
  • 排序听商店的： 检索和排序用的是商店搜索系统自己的逻辑和信号。
  • 检查每次都做： 参数范围和条数上限由执行器把关，不靠模型自觉。
  • 换一家商店也能用： 只要实现同一个后端接口，工具定义和执行器都不用改。

何时把逻辑留在系统一侧​

在以下情况下，把逻辑留在系统一侧：

  • 它需要模型看不到的数据，比如排序信号、库存和价格；
  • 它必须每次都成立，比如参数范围和条数上限；
  • 商店的系统里已经有它，比如检索和排序。

后端答不好的问题，工具也答不好。这时该在后端加一个能直接回答它的接口，而不是在工具里多调几个服务、把答案拼出来。

顾客更在意价格还是评分、哪几件值得推荐，这类要读懂对话才能做的判断，留给模型。工具边界本质上把“怎么找”交给商店的系统，把“找什么、推荐哪件”留给模型。
