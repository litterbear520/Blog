工具的定义与边界

一个 Agent 工具由两半组成：模型读到的定义，和执行器运行的代码。定义告诉模型能做什么、参数怎么填；代码把这次调用交给商店已有的系统。两半之间的那条线就是工具边界：线的一侧是模型的判断，另一侧是系统的逻辑。

在《循环与第一个工具》里，我们用一个 Python 函数在六条示例商品里做关键词匹配，跑通了一次工具调用。这一节换成参考实现里的购物 Agent：默认配置下它有 21 个工具，背后接着商店的搜索、购物车和订单系统。我们从商品搜索这一个工具出发，看这条边界是怎样划出来的。

读完这一节，您将能够说出工具定义里哪些内容是写给模型的约束，判断一段逻辑该放在工具里、后端里还是交给模型，并解释为什么工具列表的顺序是固定的。

工具边界要解决的问题​

我们用一个具体的请求来看。顾客问：“有没有 200 美元以内的双人帐篷？”要回答它，Agent 需要从商品目录里找出帐篷，去掉超出预算的，再挑出最合适的几件告诉顾客。这一课的例子都来自原型店铺，它是测试和本地原型共用的假后端，只有五件商品；其中符合条件的是 p-100，一顶 149 美元、评分 4.6 的双人徒步帐篷。

最直接的做法是把目录交给模型：把全部商品写进上下文，让模型自己筛、自己排。六条商品时这可行，但真实商店的目录放不进上下文；而且排序靠的是搜索系统多年调出来的逻辑和它掌握的信号，这些模型都看不到。

另一种做法走到另一头：在工具函数里把逻辑补齐，先查目录，再按价格过滤、按评分排序，顺手查一下库存。这也可行，但工具层成了重写后端逻辑的地方：规则一变，工具就跟着出错，而这些逻辑本来就在商店的系统里。

参考实现的答案是把工具建在已有系统之上，让两边各做自己擅长的事：

模型读到的工具定义​

模型对一个工具的全部了解，就是它的定义：名字、一段描述和参数的 JSON Schema。购物 Agent 的工具定义都写在 build_tools 里，遵守三条约定：

  1. 描述说清返回什么、什么时候用。 search_products 的描述写明返回“商品的 id、标题、品牌、价格、评分和库存状态”，并交代“顾客提到多个不同商品时，每个商品单独搜索一次”。
  2. Schema 把判断拆到字段上。 filters 的说明是“顾客明确提出的筛选条件；猜测的内容放在 query 里”。顾客说了“200 美元以内”，价格上限就写进 filters；顾客没说的偏好，只能留在关键词里。
  3. 一条描述只管一个工具。 跨工具的规则写在系统提示词里，比如“说某样东西店里没有，要先在这轮搜了两次”；不常见的流程写在技能里。

工具列表本身也有约定：顺序固定，只随部署配置变化。某个部署没开订单系统，订单相关的工具就不在列表里；但在同一个部署里，每一轮请求发出的工具定义逐字节相同，哪怕购物车是空的，update_cart_item 也照样在列表里。

您可能会问：为什么不按情况增删工具，让模型少看几个用不上的？原因有两个。第一，工具定义是请求里最稳定的一段前缀，变一个字节，这段前缀就不再命中提示词缓存，这正是规则 2 要守住的东西。第二，列表不变，模型对“能做什么”的认识也不变；某次调用在当下能不能做，交给执行器来判断。

一次搜索怎样穿过边界​

有了定义，我们跟着一次调用走一遍。以顾客的帐篷请求为例，这次往返分为五步：

  1. 模型读完定义，发出一次 search_products 调用，例如参数为 {"query": "帐篷", "filters": {"max_price": 200}}。
  2. 执行器按工具名找到处理函数。部署关掉的工具在这一步就被拦下，即使模型凭印象调用了它。
  3. 执行器整理参数：query 清洗后限制在 300 个字符以内，filters 按 SearchFilters 校验，limit 限制在 1 到 8 之间。
  4. 后端按商店自己的逻辑检索、过滤和排序，返回商品列表。在原型店铺里，这次的结果只有 p-100。
  5. 执行器把返回的商品记进这次会话的 seen_products，再把结果写成一行说明加一段围栏数据，作为 tool_result 交回模型。

教程步骤

让我们通过一个示例项目来更好地了解如何实现此功能。

我们从工具定义所在的文件开始。开头的说明写下了整份工具列表的约定：顺序固定，列表只取决于部署配置，所以每次请求发出的工具定义逐字节相同；某一次调用能不能执行，交给执行器去判断。

最后一句给描述划了范围：一条描述只管一个工具，跨工具的规则放在系统提示词或技能里。这样修改一个工具的描述时，不会牵动其他工具。

search_products 的 description 先说返回什么：商品的 id、标题、品牌、价格、评分和库存状态；再说怎样用：用具体的关键词搜索，顾客明确说的条件放进 filters，顾客提到几个不同商品时每个单独搜一次。

input_schema 里只有 query 是必填的，limit 的 maximum 是 8，additionalProperties 为 False。这些约束写给模型看，让它在生成参数时就知道边界在哪；执行器收到参数后还会自己再检查一遍，后面看到执行器时会讲。

filters 的说明是“顾客明确提出的筛选条件；猜测的内容放在 query 里”。顾客说“200 美元以内”，价格上限就写进 max_price；顾客没提、只是模型推测可能合适的条件，只能留在关键词里。

这样区分的道理在于，过滤条件会直接把商品排除在结果之外：模型猜错一个 min_rating，合适的商品就不会出现，模型也无从知道它们存在。sort 用 enum 限定为四种排序方式，并说明默认按相关度，除非顾客指定。

build_tools 的最后按部署配置拿掉关掉的系统：config.absent_tools() 给出这些工具名，内置工具和展示型工具都从列表里去掉，其余的保持原来的顺序。

这是整份列表唯一会变的地方。同一个部署里，每一轮请求发出的工具定义完全相同，这段请求前缀才能一直命中提示词缓存。

模型的调用到达执行器后，execute 把它交给 dispatch。第一行先检查部署有没有关掉这个工具：即使模型凭印象调用了列表里没有的工具，也只会收到“不是本店提供的功能；直接说明，不要推荐它”，调用不会走到后端。

接下来依次是加载技能、展示型工具和普通 handler；工具名都不认识时返回“未知工具”。dispatch 不做业务判断，只把调用交给对的函数。按参考实现的设计，Messages API 运行时、Agent SDK 工具集和 MCP 服务器都经过这同一个入口。

_search_products 先整理参数：query 经过清洗，限制在 300 个字符以内；filters 由 parse_argument 按 SearchFilters 校验，不合格时会把出错的字段告诉模型；limit 由 _search_limit 截到部署配置的上限，默认是 8。

整理好的参数交给 self._backend.search_products，执行器自己不做检索和排序。拿到结果后，它把商品记进 seen_products，再用 search_result_text 写成一行说明加一段围栏数据，交回模型。

StorefrontBackend 是采用方唯一需要实现的接口。search_products 的约定写在文档字符串里：返回最接近的文本匹配，按相关度排序，最多 limit 条；没有匹配时返回空列表。有选项的家族商品算一条结果，它的变体要通过 get_product_details 解析。

原型店铺的实现只是在五件商品上做关键词匹配和价格过滤。换成真实的商店时，只要把这个方法接到商店自己的搜索系统，工具定义和执行器都不用改。

这样划界的取舍​

把逻辑留在系统一侧，可以消除工具层重写业务规则的问题，但会带来显著的权衡：工具只能和后端一样好 —— 后端的搜索答不好的问题，工具也答不好，最容易走的弯路就是在工具里多调几个服务，把答案拼出来。参考实现的建议正好相反：发现自己在工具里写这种逻辑时，在后端做一个能直接回答这个问题的接口，再让工具去调它。

不过，有一个好处：边界清楚之后，同一套工具可以接到不同的商店。原型店铺的后端只在五件商品上做关键词匹配和价格过滤，换成真实商店的搜索系统时，工具定义和执行器一行都不用改。执行器也只有一份：参考实现里，Messages API 运行时、Agent SDK 工具集和 MCP 服务器都调用同一个 execute（路线到 Stage F 才接上后两条），这就是规则 6“每个机制只定义一次”。

在以下情况下，把逻辑放在系统一侧：

  • 它需要模型看不到的数据，比如排序信号、库存和价格；
  • 它必须每次都成立，比如参数范围和数量上限；
  • 几条运行路径都要用到它。

而这位顾客更在意价格还是评分、哪几件值得展示，这类要理解对话才能做的判断，留给模型。

到这里，一次搜索的去程已经清楚了：模型决定搜什么，系统负责搜出来。下一课我们看回程：执行器交回模型的 tool_result 该写成什么样子，为什么里面除了商品数据，还有一行写给模型的说明。
