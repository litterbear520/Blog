写给模型的工具结果

工具返回的内容会原样进入模型的上下文，模型下一步做什么，取决于它在结果里读到了什么。一段冗长的 JSON 会挤占上下文，一个笼统的错误码会让模型无从下手。所以参考实现把工具结果当成写给模型的一段话来设计：只留推理要用的字段，在结果里写明下一步，失败时也给一句能照着做的话。

上一课我们跟着一次搜索，走到执行器把结果交回模型为止。这一课接着看回程：同一个结果怎样分给模型和界面，搜索结果为什么要多一行说明，以及五种失败各自变成了一句什么话。

读完这一节，您将能够说出一个工具结果里哪些内容给模型、哪些给界面，判断一个字段该不该进结果，并为一次失败写出模型能照着做的提示。

工具结果的两个读者​

我们先看一次成功的加购。顾客说“就要这顶帐篷，加一顶”，模型调用 add_to_cart 加入 p-100。这次调用的结果要交给两个读者，而它们要的东西完全不同：

  • 模型只需要确认发生了什么，好接着和顾客说话。它收到的是一句话：“已加购 p-100 x1。购物车现有 1 件商品，小计 149.00 USD。”
  • 界面要把购物车画出来，需要每一行的标题、单价、件数和小计。它收到的是一个 cart_update 事件，里面是完整的购物车。

参考实现用一个类型装下这两份内容：执行器每次返回一个 ToolOutcome，result_text 进模型的上下文，events 交给界面渲染：

这样分开之后，给界面的数据可以很完整，而不必担心挤占模型的上下文。确认里还有一个细节：它只写商品 id，不写商品标题。代码注释说，标题是商品目录里的文本，要留在围栏里，原因在《第三方文本的围栏》一课细讲。ToolOutcome 另外两个字段记下调用的结局：is_error 标记失败，blocked 记下拦住这次调用的门控名，下一课会用到它。

只留推理要用的字段​

给模型的结果里，每个字段都要回答一个问题：模型推理时用得上吗？用不上的，就不进上下文。搜索结果里的每条商品都经过 compact_product：它只挑 14 个字段，image_url 和 category 不在其中，值为空的字段也去掉。商务指南说过，最常见的冗余就是每条搜索结果都带着一个图片 URL；图片要显示在界面上，那是界面那一路的事。

有选项的商品省得更多。原型店铺的睡垫 p-400 有常规款和长款两个变体，详情里的每个变体都经过 variant_row，只保留 id、选项值、价格、库存，以及和家族不同的字段。长款 p-400-l 前后是这样的：

写法p-400-l 在结果里的样子
完整记录{"product_id": "p-400-l", "title": "Trail 自充气睡垫", "price": 69.0, "currency": "USD", "labels": [], "attributes": {}, "in_stock": false, "options": {}, "option_values": {"length": "long"}, "variant_of": "p-400"}
变体行{"product_id": "p-400-l", "option_values": {"length": "long"}, "price": 69.0, "in_stock": false}

整条 p-400 的详情数据因此从 759 个字符减到 419 个。标题、币种和所属的家族并没有丢：它们在家族那一层已经出现过一次。

在结果里写下一步​

光看数据看不出下一步该做什么时，就在结果里附一句下一步，搜索结果是最典型的例子。顾客问“有双人帐篷吗？”，模型用“双人帐篷”去搜。原型店铺里的帐篷叫“双人徒步帐篷”，关键词匹配不上，搜索返回零条。模型实际收到的结果是：

搜索返回 0 条结果：目录中没有匹配此查询的商品。在告知顾客没有该商品之前，先用更宽泛的关键词重试一次，不要把其他商品当作顾客要找的那个。搜索匹配的是商品文本而非 id；要解析商品 id 请用 get_product_details。
<storefront_data>
{"query": "双人帐篷", "result_count": 0, "results": []}
</storefront_data>

第一行说明替模型挡住了两个常见的错误：把零结果当成“店里没有”直接告诉顾客，以及拿别的商品冒充顾客要的那个。模型照着说明放宽关键词，改搜“帐篷”，就能找到 p-100。说明的最后一句还点破了一个容易踩的坑：搜索匹配的是商品文本而不是 id，要按 id 查商品，得用 get_product_details。

有结果时，第一行换成另一句说明：这只是最接近的文本匹配，只有标题和属性都匹配，才算顾客要的商品。这一行放在围栏外面，是整个结果里唯一由运行时生成的文字，除了结果数量，每次都一样。系统提示词里也有对应的规则：说店里没有某样东西之前，要先在这一轮搜两次。

失败也写成指令​

工具失败时更要这样做。商务指南举过一个例子：与其返回一个笼统的 403，不如返回“查询库存时请带上商品 ID”。购物 Agent 的 execute 从不抛异常，每种失败都变成一句带着下一步的话。下面是在原型店铺里实跑出来的原话，其中缺货、不提供和故障三行，是让后端抛出对应的异常得到的：

情况谁发现的模型收到的话
参数不合要求parse_argument 校验 filters“search_products 的参数无效——sort: Input should be 'relevance', 'price_asc', 'price_desc' or 'rating'。调整后再调用一次。”
商品买不了后端抛出 Unavailable“未加入购物车：p-300 缺货。告知顾客，推荐消息中提到的有货替代品，只有顾客选择后才加入。”
本店不提供后端抛出 NotOffered“送货上门不是本店提供的，请直接告知顾客。”
工具出故障其他任何异常“search_policies 暂时不可用。用已有的信息继续，或者告诉顾客。”
部署没开这个系统dispatch 查到工具被关掉“get_orders 不是本店提供的功能；直接说明，不要推荐它。”

每一句都以下一步收尾，而且下一步各不相同：参数错了，改了再调；商品买不了，推荐替代品，但要等顾客选；不提供的服务，直接说；工具故障，用手上的信息继续。“不是本店提供的”和“暂时不可用”也被刻意分开：前者是事实，模型该直接告诉顾客；后者是故障，模型可以绕过它继续工作。工具出故障时，执行器还会记一条带异常栈的日志：异常栈给工程师看，模型只看那一句话。

教程步骤

让我们通过一个示例项目来更好地了解如何实现此功能。

ToolOutcome 是每个工具调用的产出，文档字符串写明了分工：result_text 给模型看，events 给调用方渲染。前者作为 tool_result 的内容进入对话，后者由编排器作为事件发给界面，不进模型的上下文。

另外两个字段记下这次调用的结局：用 error 构造的结果 is_error 为真，表示失败；用 held 构造的结果在 blocked 里写下拦住它的门控名。refused 把两者合在一起，调用方据此判断这次调用有没有被拒绝。

compact_product 是搜索结果里一条商品的写法。它只挑 14 个字段，Product 上的 image_url 和 category 不在其中。商务指南说过，最常见的冗余就是每条搜索结果都带着一个图片 URL，它对推理没有用。

最后一行去掉值为 None 的字段，labels、attributes 这类空容器也先写成 None，再一起去掉。测试 test_compact_product_omits_empty_optionals 断言的就是这件事：一件只有标题和价格的商品，结果里不会出现空的 brand、rating、options。

有选项的家族商品在详情里带着一串变体。variant_row 让每个变体保留 _VARIANT_ALWAYS 里的四个字段，也就是 id、选项值、价格和库存，再加上和家族不同的字段；和家族相同的标题、品牌都不再重复。

每一行以 id 和选项值开头，注释写明了原因：模型扫的就是这两样。原型店铺的睡垫 p-400 有两个变体，长款 p-400-l 的完整记录有 10 个字段，写成变体行只剩 4 个。

搜索结果的第一行是写给模型的说明，放在围栏外面，也是整个结果里唯一由运行时生成的文字；除了结果数量，每次都一样。有结果时，它提醒模型这只是最接近的文本匹配，只有标题和属性都匹配，才算顾客要的商品。

零结果时换成 SEARCH_EMPTY_HEADER：告诉顾客没有之前先用更宽泛的关键词重试一次，不要把别的商品当成顾客要的那个，并点明搜索匹配的是文本而不是 id。search_result_text 把这一行和围栏里的数据拼在一起，作为 search_products 的完整结果。

所有工具调用都从 execute 进来，失败在这里分成三级：参数不合要求的 InvalidArguments，回一句点出出错字段的话；角色自己的异常交给 domain_error 翻译；其余任何异常都记一条日志，再告诉模型这个工具暂时不可用。

注释写明了原因：工具失败不能让对话轮次中断。异常栈只进日志，给工程师看；模型只收到一句能照着做的话。

invalid_arguments_text 把校验错误逐条写成“字段: 原因”，最后加一句“调整后再调用一次”。模型把 filters 里的 sort 写成 cheapest 时，收到的是：search_products 的参数无效——sort: Input should be 'relevance', 'price_asc', 'price_desc' or 'rating'。调整后再调用一次。

只有 parse_argument 抛出的错误才按参数错误报告。后端自己构建记录时出的校验错误，和其他故障一样算作工具暂时不可用，免得模型以为是自己的参数写错了。

ShoppingToolExecutor 把给模型的固定措辞都写成类属性：展示成功时回“已展示给顾客。”，工具故障时回“暂时不可用。用已有的信息继续，或者告诉顾客。”，部署没开的功能回“不是本店提供的功能；直接说明，不要推荐它。”

每一句都以下一步收尾：继续、告诉顾客，或者不要推荐。框架只决定什么时候用哪一句，措辞由角色自己写，商户 Agent 有它自己的一套，比如“已展示给经营者。”。

domain_error 把后端的两种信号翻译成指令。Unavailable 表示商品存在但眼下买不了，模型收到“未加入购物车：……告知顾客，推荐消息中提到的有货替代品，只有顾客选择后才加入。”；NotOffered 表示本店不提供这项服务，模型收到“……不是本店提供的，请直接告知顾客。”

后端消息先经过清洗，限制在 200 个字符以内，因为它是围栏外到达的文本。其他异常在这里返回 None，交回 execute 按工具故障处理。

157def _before_open_string(text: str, opened: int) -> str:
158    """把文本回退到 ``opened`` 处未闭合字符串出现之前：
159    连同它的 key 和冒号一起删掉（如果它是一个 value），再去掉前面的逗号。"""
160    head = text[:opened].rstrip()
161    # 如果这个字符串是某个 key 的 value，结尾会是冒号
162    if head.endswith(":"):
163        head = head[:-1].rstrip()
164        # 冒号前面是 key 的闭合引号，往前找 key 的开始引号
165        if head.endswith('"'):
166            index = len(head) - 2
167            while index > 0 and not (head[index] == '"' and head[index - 1] != "\\"):
168                index -= 1
169            head = head[:index].rstrip()
170    # 去掉引入这个字段的逗号
171    if head.endswith(","):
172        head = head[:-1]
173    return head

176def parse_partial_json(buffer: str, *, settle_strings: bool = True) -> dict[str, Any] | None:
177    """把还在传输中的工具输入补全为可解析的对象，或返回 None。
178

179    未闭合的数组和对象会被补上闭合括号；悬挂的逗号和冒号会被去掉后重试。
180    正在写入的字符串连同其 key（或数组槽位）一起删掉，
181    标题、标签、ID 这类字段只在写完后才出现；
182    ``settle_strings=False`` 时就地闭合字符串，让文本随流式输出逐渐变长。"""
183    text = buffer.strip()
184    if not text.startswith("{"):
185        return None
186    try:
187        return json.loads(text)
188    except (ValueError, TypeError):
189        pass
190

191    def closers_for(source: str) -> tuple[str, bool, int]:
192        stack: list[str] = []
193        in_string = escape = False
194        opened = -1
195        for index, char in enumerate(source):
196            if escape:
197                escape = False
198                continue
199            if in_string:
200                if char == "\\":
201                    escape = True
202                elif char == '"':
203                    in_string = False
204                continue
205            if char == '"':
206                in_string = True
207                opened = index
208            elif char in "{[":
209                stack.append(char)
210            elif char in "}]" and stack:
211                stack.pop()
212        closing = "".join("}" if open_ != "[" else "]" for open_ in reversed(stack))
213        return closing, in_string, opened
214

215    candidates: list[str] = []
216    closing, in_string, opened = closers_for(text)
217    if in_string and settle_strings:
218        text = _before_open_string(text, opened)
219        closing, in_string, opened = closers_for(text)
220    candidates.append(text + ('"' if in_string else "") + closing)
221    trimmed = text.rstrip()
222    while trimmed and trimmed[-1] in ",:":
223        trimmed = trimmed[:-1].rstrip()
224    if trimmed != text:
225        closing, in_string, opened = closers_for(trimmed)
226        candidates.append(trimmed + ('"' if in_string else "") + closing)
227    for candidate in candidates:
228        try:
229            parsed = json.loads(candidate)
230        except (ValueError, TypeError):
231            continue
232        if isinstance(parsed, dict):
233            return parsed
234    return None

这样写结果的代价​

把结果写给模型，可以省掉很多白跑的轮次，但会带来显著的权衡：每个结果都多了字 —— 有结果时第一行说明有 90 个字符，零结果时有 117 个，每次搜索都要为它付 token；措辞也成了要维护的东西，测试里断言了其中的关键词，比如“暂时不可用”“不是本店提供的”，改措辞时要跟着改测试。不过，有一个好处：结果的格式由同一组函数统一构建，文档字符串写明是为了让每条路径返回相同的字节。按参考实现的设计，Messages API、Agent SDK 和 MCP 三条路径拿到的结果一模一样，这正是规则 6 的要求。

在以下情况下，在结果里加一句下一步：

  • 光看数据容易误读，比如零结果，或者文本匹配和按 id 查询的区别；
  • 失败有好几种，而每种的正确反应不同；
  • 结果交给顾客之前，模型还得先做一个判断，比如缺货时先推荐、等顾客选。

数据本身已经说明一切时，就不必再加话。get_orders 有订单时直接返回订单，一张都没有时才附一句“没有找到订单。”；多一句话，就多一份要维护的措辞。

结果写清楚了，模型就知道下一步该做什么。但有一类调用，我们不能只靠模型读懂结果再自觉照做：它们会改动购物车。下一课我们看执行器怎样在写入之前把关。
