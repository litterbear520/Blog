写给模型的工具定义

模型看不到工具的代码，它对一个工具的全部了解就是定义：名字、描述和参数说明。定义写清返回什么、参数怎么填，模型才会用对这个工具。整份工具列表也保持不变，每次请求都逐字节相同。

工具定义解决的问题​

假设顾客问：“有没有 200 美元以内的双人帐篷？”模型要把这句话变成一次搜索：关键词写什么，哪些条件放进筛选。但问题在这里——这些都只能从定义里读出来。您有两个选择：

选项 1： 定义里只写名字和参数类型。模型只好猜每个参数怎么用，比如以为顾客想要好评的，顺手加上“评分 4.8 以上”。那顶评分 4.6 的帐篷就被筛掉了，模型也无从知道它存在。

选项 2： 把用法写进定义。筛选条件（filters）的说明写着：只放顾客明确提出的条件，猜测的内容放进关键词（query）。模型就只把“200 美元以内”放进筛选。

工具定义的工作原理​

每次请求，模型都这样使用工具定义：

  1. 模型读到的内容里，最前面是整份工具列表，每个工具一个名字、一段描述和参数的 schema用 JSON Schema 写的参数说明：有哪些字段、每个字段的类型、说明和取值范围。
  2. 模型读描述，挑出该用的工具。搜索工具的描述写明它返回价格、评分和库存，还交代顾客提到几样东西时要分开搜。
  3. 模型照参数说明填参数：顾客明确说的放进筛选，猜测只写进关键词。
  4. 模型在 schema 写明的范围里取值，比如排序方式只能四选一，一次最多要八条结果。
  5. 执行器收到调用，按自己的规则再检查一遍。定义里的约束写给模型看，真正的把关在执行器。

工具列表为什么不变​

工具列表的顺序固定，只随部署配置变化。某个部署没开订单系统，订单相关的工具就不在列表里。

在同一个部署里，每次请求发出的都是同一份列表。哪怕购物车是空的，改购物车的工具也照样在里面。下面是连续三次请求：

三次请求都以同一份工具列表开头，接着是提示词，最后是一次比一次长的对话。列表这样保持不变，有两个原因：

  • 缓存保持命中： 提示词缓存API 把请求开头的内容缓存起来；下一次请求开头逐字节相同时直接复用，更快也更便宜从请求开头逐字节比对，工具列表排在最前面。列表变一个字节，整段缓存就要重新写入。
  • 模型的认识不变： 列表不变，模型对“能做什么”的认识就不变。某次调用此刻能不能执行，交给执行器判断。

何时把规则写进工具定义​

一条描述只管一个工具。在以下情况下，把规则写进工具定义：

  • 它说明这个工具返回什么、什么时候用；
  • 它决定某个参数该怎么填；
  • 它限定参数的取值范围，比如排序方式和条数上限。

跨工具的规则写进系统提示词，比如告诉顾客店里没有某样东西之前，要先在这一轮搜两次。工具定义本质上是写给模型的使用说明：模型读它决定怎么调用，执行器再替系统把关。
