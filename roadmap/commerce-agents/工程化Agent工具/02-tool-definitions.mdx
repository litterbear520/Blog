# 写给模型的工具定义

<LessonMeta lesson={2} minutes={6} />

模型看不到工具的代码。它对一个工具的全部了解，就是工具列表里的那份定义，所以定义要写成给模型看的使用说明。

## 一份工具定义的三个部分

以搜索工具为例，模型读到的定义是这样的：

<Diagram variant="toolDefinitionParts" />

- **名字（`name`）：** 模型调用工具时写的就是它。
- **描述（`description`）：** 说清工具返回什么、什么时候用。搜索工具的描述写明它返回价格、评分和库存，还交代顾客提到几样商品时要分开搜。
- **参数说明（`input_schema`）：** 每个参数的类型、取值范围和用法，比如一次最多要八条结果。

## 把用法写进参数说明

参数说明决定模型怎么填。假设顾客问：“有没有 200 美元以内的双人帐篷？”同一个筛选参数（`filters`），写不写用法，结果不一样：

<Diagram variant="toolDefinitionOption1" />

**只写类型：** 模型只好猜筛选条件怎么用，比如以为顾客想要好评的，顺手加上“评分 4.8 以上”。那顶评分 4.6 的帐篷就被筛掉了，模型也无从知道它存在。

<Diagram variant="toolDefinitionOption2" />

**写明用法：** 说明写着：只放顾客明确提出的条件，猜测的内容放进关键词（`query`）。模型就只把“200 美元以内”放进筛选。

请记住，定义里的约束是写给模型看的。执行器收到调用后，还会按自己的规则再检查一遍，真正的把关在执行器。

## 工具列表为什么不变

工具列表的顺序固定，只随部署配置变化。某个部署没开订单系统，订单相关的工具就不在列表里。

在同一个部署里，每次请求发出的都是同一份列表。哪怕购物车是空的，改购物车的工具也照样在里面。下面是连续三次请求：

<Diagram variant="toolListRounds" />

三次请求都以同一份工具列表开头，接着是提示词，最后是一次比一次长的对话。列表这样保持不变，有两个原因：

- **缓存保持命中：** <Term tip="API 把请求开头的内容缓存起来；下一次请求开头逐字节相同时直接复用，更快也更便宜">提示词缓存</Term>从请求开头逐字节比对，工具列表排在最前面。列表变一个字节，整段缓存就要重新写入。
- **模型的认识不变：** 列表不变，模型对“能做什么”的认识就不变。某次调用此刻能不能执行，交给执行器判断。

## 何时把规则写进工具定义

一条描述只管一个工具。在以下情况下，把规则写进工具定义：

- 它说明这个工具返回什么、什么时候用；
- 它决定某个参数该怎么填；
- 它限定参数的取值范围，比如排序方式和条数上限。

跨工具的规则写进系统提示词，比如告诉顾客店里没有某样东西之前，要先在这一轮搜两次。工具定义本质上是写给模型的使用说明：模型读它决定怎么调用，执行器再替系统把关。
