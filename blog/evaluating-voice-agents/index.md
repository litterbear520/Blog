语音代理可能通过了你为它写的每一项评测，到了生产环境却照样出问题。转录文本读起来没问题，工具调用的参数也对，后端数据也改对了，评分卡把这通电话记为成功。可当你去听真实录音，却听到代理和来电者抢话，把对方的名字念错，在确认任何信息之前还冷场了三秒。

{/* truncate */}

这样的落差我不止一次亲眼见过，原因总是同一个：人们把语音代理当成接了麦克风的文本代理来评估。语音代理是一个实时分布式系统，它的产品质量大多体现在转录文本根本反映不出来的地方，比如代理什么时候开口、用户等了多久、被打断时有没有让出话头，以及它做这些事时听起来怎么样。只在通话结束后读转录文本的评测，评的其实是这次交互的摘要，而不是交互本身。

我在写[语音代理入门](https://manthanguptaa.in/posts/voice_agents_primer)时提到过，标准的 LLM 评测完全测不出这些问题，并把评估这个话题留到了以后。完整的评估必须覆盖通话本身：选对评估单位，给通话的四个层面打分，弄清你的模拟器和 LLM 裁判（用 LLM 给通话打分）是否可信，再把结果变成“发版还是不发版”的决定。

这是语音代理系列的第三篇，也是最后一篇，前两篇分别是[语音代理入门](https://manthanguptaa.in/posts/voice_agents_primer)和[语音代理的记忆](/blog/voice-agent-memory)。

我们开始吧。

## 评估的单位是通话

最简单的评测做法是把音频转成文字，交给 LLM，再给回复打分。这能衡量代理在转录之后有没有给出合理的回答，却测不出这些问题：等得太久、打断用户、用户插话打断（barge-in）时不理会、听错关键信息、听起来无精打采、在背景噪声里照说不误，以及后端操作没做对。

现在的语音评测评估的是实时通话的整条链路，而不是一条孤立的回复。这更能代表产品质量，因为目标是做出一个让用户觉得尽可能自然、尽可能有帮助的语音代理。各种语音评测工具的共同模式是：

1. 定义场景。
2. 打一通真实或模拟的电话。
3. 采集完整的追踪记录（trace）。
4. 用多个评估器给行为打分。
5. 把失败变成回归测试。

## 一个真实的评测场景

假设有一个帮诊所处理预约的语音代理。一个不够好的评测长这样：

```text
用户：我想把预约改到周五下午。
预期：代理完成改期。
```

对文本代理来说，这样的评测也许足以检查逻辑是否正确。对语音代理来说，它漏掉了时机、音频、轮流发言、工具执行和业务结果，而这些都影响产品质量。

有用的评测场景要包含来电者画像、音频条件、预期的工具行为、成功标准和失败归因：

```yaml
scenario: reschedule_existing_appointment
persona:
  name: "急性子的复诊患者"
  speaking_style: "语速快，会打断一次，日期说得含糊"
  environment: "车载蓝牙，有轻微路噪"

initial_state:
  patient_id: "p_123"
  existing_appointment: "2026-05-27 10:30"
  available_slots:
    - "2026-05-29 14:00"
    - "2026-05-29 16:30"

caller_goal:
  把预约改到周五下午

required_behavior:
  - 修改预约前先核验患者身份
  - 日期有歧义时，问清是哪个周五
  - 提供下午的可选时段
  - 用选定的时段调用 reschedule_appointment
  - 口头确认新的预约时间

failure_modes_to_track:
  - 漏掉身份核验
  - 日期解析错误
  - 工具参数错误
  - 忽略打断
  - 响应延迟 p95 超过 900ms
  - 用户把同样的信息重复了两遍
```

## 模拟跑通了，也几乎说明不了什么

语音代理有双重随机性：模型每次生成的回复可能不同；<Term tip="自动语音识别，把用户的语音转成文字">ASR</Term> 或<Term tip="判断用户这一轮是不是真的说完了、该轮到代理开口，通常会综合停顿和语义">轮次检测</Term>拿不准时，音频稍有变化，判断结果也可能不同。一通电话成功，只能说明代理有可能成功，不能说明它可靠。每个重要场景都要反复运行，并报告通过率。

这就是 [EVA-Bench](https://arxiv.org/abs/2605.13841) 同时报告 `pass@k` 和 `pass^k` 的原因。`pass@k` 问的是 *k* 次运行中是否至少有一次成功，衡量的是系统的上限。`pass^k` 估算 *k* 次独立运行全部成功的概率，衡量的是一致性。`pass@3` 高而 `pass^3` 低的系统可以做出惊艳的演示，但要用在每通电话都很重要的工作流里，它还不够可靠。

模拟器本身也需要评测。模拟来电者的用处在于能大规模运行，但它们并不等于真人。它们可能说话太标准，代理一反问就很配合，没有真人说话时的磕绊和口误，或者和被测代理同属一个模型家族、带着相同的怪癖。要用一组专门留出来、不参与调优的真人通话来验证模拟器的行为：对比任务路径、打断模式、轮次长度、失败类别和通过率。如果模拟通话上的改进，换到真实通话上看不到效果，那你只是在针对模拟器做优化。

## 第 1 层：它听清用户了吗？

ASR（自动语音识别）评估通常从**词错误率**（Word Error Rate，WER）开始，WER 现在依然有用。如果你换了一家 <Term tip="和 ASR 基本是一回事">STT</Term>（语音转文字）供应商，领域 WER 从 7% 跳到 14%，那你很可能把代理变差了。不过，错误率对业务的影响，取决于转录错的是哪些词。

把 “the” 转录成 “a” 可能无伤大雅。但把 “May fifteenth”（5 月 15 日）听成 “May fifty”（5 月 50），漏掉 “not” 这个词，把药名转录得面目全非，或者把 “cancel my subscription”（取消订阅）听成 “cancel my description”（取消描述），都可能毁掉这通电话。有时候，整个任务就系于一个词。

对生产环境的语音代理，我会跟踪三个 ASR 指标：

**领域 WER** 衡量你实际用到的词汇转录得准不准：产品名、客户姓名、地址、预约类型、保险术语、SKU、机场代码，总之是你这个领域会出现的词。这个指标要用真实通话来算。

**实体错误率**衡量决定业务逻辑的字段有没有听对：姓名、日期、金额、确认号、地址和各类 ID。它往往比 WER 更能预示通话的成败。一份转录文本可以 95% 正确，这通电话却依然失败，因为那 5% 里恰好有预约时间。

**流式稳定性**衡量中间转录结果在定稿之前变动了多少。如果代理拿到中间的 ASR 结果就开始规划下一步，只看最终 WER 就已经晚了。你需要知道的是，中间转录结果是否足够稳定，能不能拿去做轮次检测、提前判断意图或提前规划工具调用。

这里有个不易察觉的问题：归因。如果 ASR 把 “Friday at four”（周五四点）转录成 “Friday at floor”（周五在楼层），LLM 可能会反问一个莫名其妙的问题。只看转录文本的评测会把账算到 LLM 头上，以为它犯糊涂了，其实是 ASR 给了模型错误的输入。

## 第 2 层：它把控好对话了吗？

这正是文本评测完全覆盖不到的部分。

语音是在连续的时间里展开的。用户会停顿、换气、附和（backchannel）、改口、和代理抢话，还会在代理答到一半时换个问题。好的语音代理既要答得好，也要把得住对话节奏。把打断逻辑做对只完成了一半工作，你还得衡量它在各种真实条件下是否都管用。

学术界已经开始在这方面追赶。[Full-Duplex-Bench](https://github.com/daniellin94144/full-duplex-bench) 评估停顿处理、附和、轮流发言和用户打断。它的 v1.5 版本加入了声音重叠的场景，包括打断、附和、用户和别人说话以及背景人声，并衡量模型是停下、回应、恢复说话，还是错误地一直占着话头。其中的时间指标，正是生产团队应该从 Full-Duplex-Bench 搬进自己评测的那类东西：被打断后多久停下、打断后多久回应；另外还要看模型有没有真正转向用户的新意图。

之所以要看这些指标，是因为单看“打断次数”说明不了什么。打断次数高，可能说明用户听得投入，正在自然地附和；也可能说明代理太啰嗦，用户一直在打断它。你需要跟踪下面这几类指标：

**语音结束检测准确率**：代理是判断出用户说完了才开口，还是用户一停顿就抢着开口？

**让步延迟**（yield latency）：用户打断时，代理还继续说了多久？

**附和语甄别**：当“嗯嗯”“对”只是表示在听时，代理有没有忽略它们？听到“等等，其实……”时，它有没有停下来？

**代理抢话率**：用户还没说完，代理就开口的情况有多频繁？

**静默预算**：用户在整通电话中总共经历了多少冷场？尤其要看 p90 和 <Term tip="把所有数值从小到大排，99% 都不超过的那个值，代表最差的那 1% 的情况；p50、p90、p95 同理">p99</Term>。

很多“模型不行”的抱怨，其实是在抱怨这一层的 <Term tip="语音活动检测，判断音频里有没有人在说话">VAD</Term>、<Term tip="根据停顿判断用户这段话在哪里结束">端点检测</Term>（endpointing）或轮次检测。端点检测器触发得太早，代理就会对着半句话作答；触发得太晚，通话就显得迟钝。打断检测太灵敏，代理会因为咳嗽和背景电视声而停下；太保守，用户就会觉得插不上话，像被困住了一样。

### 要看每一段的延迟，不能只看总耗时

端到端延迟告诉你用户等了多久，要找出为什么等这么久，就得追踪流水线的每个阶段，把总耗时拆成一段一段（这种分解图叫延迟瀑布）。把单独一轮对话从头到尾追踪一遍：用户停止说话；端点检测器判定这一轮确实结束；ASR 给出稳定的转录结果；LLM 输出第一个 token（如果这一轮要调用工具，则依次是生成工具调用、工具自身执行、模型再处理一遍工具结果）；<Term tip="文字转语音，把代理要说的话合成成声音">TTS</Term> 合成出第一帧音频；最后经过网络缓冲和播放，用户才真正听到声音。实际上这些阶段会互相重叠，不是整齐地排成一条线，所以要把每一段都记成追踪跨度（trace span），不能只记一个总数。

唯一能代表产品体验的指标是**轮次结束到首个音频的时间**（end-of-turn time to first audio，TTFA），也就是从用户说完这一轮，到听见代理第一声回应的时间，要看它的 p50、p95 和 p99。追踪里的其他数据都只是用来诊断的。一通电话慢，问题可能出在过于保守的端点检测、不稳定的中间转录、LLM 的首 token 时间、工具调用的生成、工具的<Term tip="最慢的那一小部分请求的耗时，比如 p99">尾部延迟</Term>、工具调用后的模型处理、TTS 启动或<Term tip="播放前先缓存一小段音频，抵消网络时快时慢的影响，缓存越多延迟越高">抖动缓冲区</Term>上；在看到分解数据之前，你说不清该修哪一个。没有分解数据，团队往往会去优化仪表盘上最显眼的那个组件，而不是真正耗费用户时间的那个。

用到工具的轮次需要特殊对待，因为其中可能有两段静默：一段在代理先应一声之前，一段在工具运行期间。两段都要测量。即使后端操作耗时较长，先快速应一声也能让交互显得灵敏；但在工具成功之前，这声回应不能变成虚假的保证。

## 第 3 层：它想对、做对了吗？

代理听清了用户、也把控好这一轮之后，接下来用四项检查来评估它的推理和行动。

**意图和状态跟踪**：代理明白用户想要什么了吗？它有没有在多轮对话中保留相关状态？在语音里，同一个意图常常分成好几段零碎的话说出来：“我想改一下……不不，不是明天……周五那个……有下午的话就下午。”评测应该验证最终状态，而不只是检查每一轮。

**工具调用正确性**：代理有没有在正确的时机、用正确的参数调用正确的工具？这一项应该直接比对结构化数据，不要靠读文字来判断。

**业务结果**：后端数据真的改对了吗？成功意味着预约改了、退款发了、工单建了，或者转接到了正确的队列，而不只是代理说了一句“都办好了”。

**合规和安全**：代理遵守你的领域里重要的规则了吗？医疗、金融、保险和招聘领域的代理，都有一些步骤不能只做到“基本正确”。身份核验、用户同意、信息披露、转人工和 <Term tip="个人身份信息，比如姓名、电话、证件号">PII</Term> 处理，都必须用非过即挂的硬性断言来检查。

LLM 裁判（LLM-as-judge）在这一层派得上用场，也就是让 LLM 按评分标准给通话打分，但前提是标准要具体。“代理有帮助吗？”是弱标准。“代理在透露预约详情之前核验身份了吗？”是强标准。“代理在完成取消之前，说明会收取取消费用了吗？”是强标准。“代理是否做到了在核实资格之前不承诺退款？”是强标准。

好裁判都很无聊，读起来就像 QA 检查清单。

### 你的裁判也需要评测

LLM 裁判只是系统里的又一个模型，不是标准答案。在把它用作发布门禁之前，先从真实通话中构建一套人工标注的校准集，再按评分标准的每个维度，测量裁判和人工标注的一致程度。误判通过和误判失败要分开跟踪：裁判偶尔把礼貌程度打低只是让人烦，漏掉违规行为就危险了。

对自然度、简洁度这类主观比较，两两对比往往比绝对打分更容易校准。A/B 和 B/A 两种顺序都要跑，因为裁判可能总是偏向排在某个位置的那一个。锁定裁判的模型、提示词、评分标准和版本，并把它们和每个分数一起记录下来；其中任何一项变了，都要重新校准。最近一项关于[裁判可靠性](https://arxiv.org/abs/2606.19544)的大规模研究发现，裁判重复打分时结果很一致，同时也可能有明显的位置偏差。所以，只凭“裁判给的分很稳定”，还不足以验证这个裁判没问题。

结构化的事实根本不该交给 LLM 裁判。工具名称、参数、调用顺序、后端状态、延迟，以及明确的核验或披露事件，只要追踪记录里有，就应该直接检查。如果合规与否只能从对话内容里判断，就用校准过的裁判或人工审查。LLM 裁判要留给真正需要解读的维度。

## 第 4 层：它听起来好吗？

在语音产品里，TTS 质量的评估至今还少得出奇。团队可以花一周时间对三版 LLM 提示词做 A/B 测试，选声音时却只看它在控制台预览里听着还行。一旦通话变长，这就不够了。

生成的音频需要单独过一遍评估。先做那些显而易见的检查：<Term tip="音量超过上限，波形被削平，听起来发破">削波</Term>、掉音、音量起伏、奇怪的停顿、重复循环的音频、发音错误，以及首个音频的延迟。这些都覆盖到之后，你还需要一个自动的自然度评分，因为没人能听完每一通电话。语音研究界有几个模型试图预测真人会给一段音频打多少分，它们算不上完美的裁判，但用来初筛很有用。

它们大多基于同一个概念：**MOS**，即平均意见得分。在经典的听音测试中，人们按 1 到 5 分给语音打分，从“差”到“优秀”，这些评分的平均值就是 MOS。听音测试无法大规模进行，所以团队改用经过训练的神经模型，直接根据音频估算这个人工分数。

**UTMOS** 就是这样一种预测模型，专为合成语音打造。把代理的 TTS 音频交给它，它会返回一个类似 MOS 的自然度分数。可以把它看作对这个问题的快速回答：“这个声音听起来像真人，还是像机器人在照着稿子念？”它适合用来比较不同的声音，以及发现 TTS 改动后质量有没有下降，但它不会告诉你电话号码有没有念错。

**NISQA** 及其 TTS 变体 **NISQA-TTS** 更进一步，不需要干净的参考录音作对比，就能给语音质量打分。这在生产环境中很重要，因为你手上通常只有发出去的那段音频，没有完美的原始录音。除了一个总分，NISQA 还把质量拆成噪声、<Term tip="声音的音色被信道或处理改变，听起来发闷或发尖">音染</Term>、不连续性和响度等维度，帮你区分“声音听起来像机器人”和“通话链路把音频弄坏了”。当你不满足于一个自然度数字，还想大致看出音频*为什么*听着不好时，就用它。

**DNSMOS** 针对的是另一个问题：音频已经经过噪声抑制、电话编解码器，或者其他会损伤音质的信道。如果你的代理运行在电话线路、蓝牙或嘈杂的房间里，DNSMOS 往往比主要用干净录音棚语音训练的模型更合适。它能帮你判断*传输链路*是否让人更难听清，而不只是 TTS 声音本身是否悦耳。

**反向 ASR** 是一种简单粗暴但实用的检查，专门抓那些自然度模型漏掉的问题。取代理本来要说的文本，用 TTS 合成出来，再用一个强大的语音转文字模型转录生成的音频，把转录结果和原文对比。如果代理本来要说 “May fifteenth”，转一圈回来却成了 “May fifty”，那就是 TTS 念错了，哪怕这段音频的自然度得分依然不错。这个办法很粗糙，却能抓到 MOS 预测模型经常漏掉的单词级错误。

前沿方向正在转向从数据里学出来的语音裁判。[SpeechJudge](https://arxiv.org/abs/2511.07931) 让人从成对的语音里挑出更好的一段，做成数据集，再训练一个判断自然度的生成式奖励模型（generative reward model，GRM）。它的结果表明，即便是强大的音频模型，也仍然难以达到人类对自然度的判断水平：SpeechJudge-GRM 在其基准上的准确率为 77.2%，加上推理时缩放（inference-time scaling）后升到 79.4%。

所以，自动音频指标只能用来初筛，不能当最终结论。最后一公里，仍然需要真人去听真实的通话。

## 我会搭建的评测框架

如果让我从零开始搭建语音代理评测，我会从五个数据集入手。

第一个是**黄金场景集**：50–100 个手写场景，覆盖用户最核心的使用流程。每个场景都有来电者画像、初始后端状态、预期工具调用、预期最终状态和合规要求。这就是你的 CI 测试套件。

第二个是**真实通话回归集**：生产环境里失败、被转人工、拿到 <Term tip="客户满意度评分">CSAT</Term> 差评或触发人工审查的通话。保留音频、时间信息、转录文本、工具追踪和结果。这是你将拥有的最有价值的数据集。

第三个是**扰动与韧性集**：同样的核心场景，放到各种口音、背景噪声、快语速、长停顿、打断、远场音频、电话编解码器和蓝牙那样的音质劣化下运行，再加上丢包、抖动、重连、工具超时、webhook 延迟和后端部分故障。它要验证重试不会造成重复预约或重复付款，通话中断也不会让后端处于不明确的状态。

第四个是**留出的发布集**：一批有代表性的场景，写提示词、调模拟器和校准裁判时都不能直接用。回归套件用到最后，都会变成团队专门对着优化的目标。一个调优时碰不到的发布集能告诉你，新版本是真的具备了泛化能力，还是只学会了这些测试。不过，反复根据它决定发不发版，它的信息还是会通过模型选择，一点点漏进最后选中的版本里，所以要定期轮换这个集合，并为重大版本另留一个更小的、从没动过的审计集。

第五个是**人工审计样本**：每周 10–20 通电话，由真人实际去听。不是读，是听。耳朵能捕捉到转录文本掩盖掉的别扭之处，这些审查也提供了必要的标注，让模拟器和自动裁判不至于走样。

每次运行都存储结构相同的追踪记录，并按你将来调试时需要的内容分组：

| 类别 | 存储内容 | 为什么要存 |
| ---- | ---- | ---- |
| 身份 | `call_id`、`scenario_id`、构建版本和供应商版本 | 以后能原样重跑同一套系统 |
| 音频 | 呼入和呼出音频、带时间戳的 TTS 分块 | 真人和音频裁判能听到真实的通话 |
| 听觉 | 中间和最终的 ASR 转录、实体提取结果、置信度 | 能分清是模型糊涂了，还是喂给它的本来就是垃圾 |
| 轮流发言 | VAD 事件、端点检测决策、打断标记 | 能衡量让步延迟和打断行为 |
| 推理 | LLM 输入和输出、工具调用及结果 | 能对意图、参数和合规步骤做断言 |
| 时间 | 延迟时间线、传输事件、重试 | 一通慢电话能拆成瀑布图，而不只是一个数字 |
| 结果 | 最终后端状态、裁判分数、人工审查备注 | 能拿“都办好了”和实际发生的变化对照 |

这些追踪记录同时也是隐私隐患。原始音频可能包含生物特征、支付信息、健康信息、地址，以及来电者说出口的其他任何内容。音频、未脱敏转录、已脱敏转录、元数据和聚合指标要分开，各自规定保留多久。在大范围搜索或分析之前先脱敏，限制对原始追踪记录的访问，并记录哪些第三方 STT、LLM、TTS 和裁判服务收到过这些数据。评测系统不该成为生产通话所有副本中管理最松的那一份。

每个层面的打分内容和门禁可以这样定：

| 层面 | 打分内容 | 门禁示例 |
| ---- | ---- | ---- |
| ASR | 实体错误率、领域 WER、流式稳定性 | 关键实体正确 |
| 轮流发言 | 端点检测、让步延迟、附和语甄别 | 被打断后 500 毫秒内停下 |
| 代理推理 | 意图、状态跟踪、合规性 | 完成必需的核验 |
| 工具 | 工具名称、参数、顺序、最终状态 | 后端状态符合预期 |
| 音频输出 | <Term tip="首字节时间，这里指开始输出音频前等了多久">TTFB</Term>、自然度、瑕疵、发音 | 没有削波或掉音，术语发音正确 |
| 结果 | 任务成功、转人工是否正确、用户情绪 | 场景达成业务目标 |

### 把分数变成发布决策

不要把所有指标平均成一个让人安心的数字。合规、安全、身份核验、必需的信息披露、工具参数和最终后端状态，都需要**硬性门禁**：只要有一次严重违规，无论延迟和自然度看起来多好，这个场景都算失败。延迟、ASR 和音频瑕疵用阈值把关，加权分或偏好分则留给语气、简洁度这类较软的品质。

关键场景要运行多次，能不能发版要看可靠性，不能看最好的那一次。报告通过率时要附上样本数和置信区间：十通电话得出的 90%，和一千通电话得出的 90%，不是同等分量的证据。要单独跟踪时好时坏的比例（flake rate），因为一个明显变得更可靠的版本，可能比一个只把裁判平均分提高了一点的版本更有价值。

每个重要指标都要按语言、口音、设备、编解码器、地区、通话时长、意图和客户群体分组来看。汇总后的 WER、延迟或任务成功率，可能掩盖集中在某一组里的失败。发布报告既要展示总体数字，也要展示样本量足够、表现最差的分组，并附上样本数和不确定性。用户体验到的是他们所在的那一组，不是你的平均值。

有用的指标，是能告诉你下一步该做什么的指标。实体错误率不过关，就检查 ASR 和领域词汇。让步延迟不过关，就检查 VAD、<Term tip="回声消除，防止代理把自己的声音当成用户在说话">AEC</Term>、打断逻辑和音频播放取消。工具参数不过关，就检查状态跟踪和 schema 设计。自然度不过关，就检查 TTS 声音、文本分块、发音词典和回复长度。如果任务成功率不过关，而所有组件指标都通过，那很可能是场景设计或业务流程本身有问题。

## 生产环境的闭环

真实通话失败时，不要只在仪表盘上打个标签。对于对话路径可以固定的测试（比如 ASR 测试、音频测试和组件测试），直接回放原来的音频。做端到端回归时，要把这次失败的条件和意图保留在一个自适应场景里，这样当改动后的代理走了另一条路径时，模拟来电者也能接得上话。

在实践中，这个闭环是持续不断的。你发布一个版本，监控真实通话，发现失败，标注根因，把这次失败变成回归测试，修复底层问题，重跑测试套件，然后才再次发布。回归测试是大多数团队跳过的环节。没有它，同样的失败可能在三个版本之后再次出现，看起来还像一个新 bug。

久而久之，你的评测集会变成一张地图，标出用户实际做过的每一件怪事：有人在车里打电话，有人每句话都要打断，有来电者把“对”当附和语，有客户背景里电视吵闹，有患者报日期不说年份，还有愤怒的用户拒绝按正常流程走。

回归集需要维护。对几乎相同的失败去重，保留原始案例，以及由它规范化或改成自适应场景后的测试，给场景和评分标准做版本管理，并让留出的发布集和日常的提示词调优保持隔离。否则，测试会越跑越慢，团队也会慢慢只对着一座“旧事故博物馆”做优化。

这样一份持续维护的数据集，比任何通用基准都更有价值。

## 结语

语音评测之所以难，是因为产品本身就是整场实时交互：用户说了什么，系统听到了什么，代理什么时候回应，听起来怎么样，有没有让出话头，调用了哪些工具，以及现实世界里发生了什么变化。

所以，要评估通话，而不是文字。
